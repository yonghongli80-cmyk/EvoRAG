## Current transaction contract relevant to these commands

`rag/db/connection.py` defines the shared `ConnectionManager`. `transaction(immediate=True)` takes the writer `RLock`, issues `BEGIN IMMEDIATE` only when no transaction is open, and commits on clean exit or rolls back on exception. If the connection is already in a transaction, a nested context silently reuses it and provides neither a savepoint nor independent rollback. `write_connection()` only serializes access; it does not begin or conclude a transaction. `read_connection()` is a thread-local query-only connection, not a multi-call read snapshot contract. `rag/user_db.py`'s `transaction()` and `locked_transaction()` both forward to the manager.

The map distinguishes the component that actually begins/commits a transaction from helpers that happen to be called inside it. Direct `conn.commit()` or `_conn.commit()` and separate private stores are called out explicitly. The shared writer serializes UserDB writes locally; that does not fence another process or coordinate files, Qdrant, or private SQLite stores.

## 3. Controlled recovery of a historical staging path

| Step | Shared SQL connection / owner | Commit and rollback boundary | Other effects and recovery |

| Recheck authorization/state | Inside the outer transaction, `_require_actor_and_acl(db, request)` reloads actor/ACL through `UserDB` and authorization helpers; these calls may use `ConnectionManager.read_connection()` rather than the writer connection. **Boundary:** archive recovery's transaction covers SQL CAS and receipt only. The archive copy is a filesystem effect and is not rolled back by SQLite. The recovery protocol deliberately preserves the original file and uses hash verification, conditional updates, operation-key receipt replay, and fail-closed conflict handling; it does not claim distributed atomicity.

## Proof limits and unknowns

- These are three call-chain reviews, not a complete call graph of every caller, worker runner, script, startup migration, direct connection or private store. No absence-of-marker conclusion is used.
- The review distinguishes visible source ownership and effect ordering; it did not execute application code, SQL, a database, tests, scanner, network or service. It does not validate runtime deployment topology or all process-crash windows.
- No global/distributed atomicity, exactly-once side effect, PostgreSQL compatibility, migration readiness, multi-instance readiness, live shadow-read permission, or cutover readiness is inferred.
- Repeated `ConnectionManager.transaction()` calls may share one transaction only when actually nested on the same shared connection; their function names alone do not prove nested caller context.
- Qdrant and private-store compensation semantics, filesystem behavior under external concurrent mutation, receipt reconciliation after uncertain commit, and exhaustive worker retry paths require the proposed synthetic cases and further source review.
- Static SQL/writer tools can bind evidence to a source snapshot and identify candidate markers; they cannot prove that a rationale is semantically correct, that SQL is safe, that all writers were found, or that the source is PostgreSQL-portable.
