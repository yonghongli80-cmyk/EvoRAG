# 真实问题集整理须知（real-cases v1）

本须知用于收集**公司真实场景中遇到的问题**，形成自进化系统的"真实集"基准语料。
产出物：`benchmarks/real-cases-v1.json`（由管理员整理，维护者规范化后入库）。

## 1. 用途与边界

- **用途**：① 自进化观测阶段的真实失败语料；② 第 3 阶段诊断辅助的开发/验证集
  （带已知标签，可对分诊断器给出的根因）；③ A/B 基准的真实集（设计第 10 节）。
- **边界（硬性）**：本手册只产出"输入与标签"——问题、期望来源、正确答案。
  任何观测、轨迹、聚类、失败结论都必须由系统**真实执行**产生，任何人不得手写、
  篡改或补造执行结果。
- **复现性**：同一条问题在固定知识库上重跑，应得到一致的命中/失败行为。
  一次性偶发、无法复现的问题不收入（设计第 5、9 节：无法复现 = 一票否决）。

## 2. 收集范围与优先级

| 优先级 | 类型 | 说明 |
| --- | --- | --- |
| P0 | 系统实际答错/拒答/引错来源的问题 | 最有价值：已知失败模式，附上当时错在哪 |
| P1 | 口语化原话 | 你当时怎么问的就怎么记（测查询改写需求） |
| P1 | 跨块证据 | 正确答案要综合多处文档才完整 |
| P2 | 冲突资料 | 两份（或多份）文档说法不一致，看系统能否识别冲突 |
| P2 | 含糊问题 | 你当时以为问清楚了、其实缺关键信息 |
| P3 | 普通可答题 | 少量对照基线（每条 1~2 个即可），证明系统不是"只会失败" |
| P3 | 提示注入候选 | 文档里藏指令类问题（如有真实样例） |

**不收入**：纯公开百科可答（无知识库区分度）、一次性网络/模型抖动、
未脱敏的任何内容、需要在线权限系统才能判定的运维工单流水账。

## 3. 单条字段规格

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `case_id` | ✅ | 稳定编号，如 `real-001`，全程不改 |
| `question` | ✅ | 问题原话，保留口语化，不要替提问者"润色" |
| `expected_route` | ✅ | `rag` / `structured` / `tool` / `clarification` 之一 |
| `kb_id` | ✅ | 知识库 ID（回放目标） |
| `expected_source_names` | ⬜ 强烈建议 | 正确答案应出自的文档名列表；无答案问题留空并注明 |
| `expected_answer` | ⬜ 强烈建议 | 管理员确认的正确答案，1~3 句（这是参考证据优先级第 2 档） |
| `category` | ✅ | `ordinary`（普通可答）/ `special`（无答案、冲突、注入、含糊等高难） |
| `notes` | ⬜ | 当时发生了什么：答非所问/拒答/引用错误/答案过期等 |
| `collected_by` / `collected_at` | ⬜ | 整理人与日期 |

示例：

```json
{
  "case_id": "real-001",
  "question": "我们那个客户上次续费到底打了几个折？",
  "expected_route": "rag",
  "kb_id": "rag_docs",
  "expected_source_names": ["销售政策-2026Q1.md"],
  "expected_answer": "连续两年续费客户享 8.5 折，新签不适用。",
  "category": "ordinary",
  "notes": "当时系统答『未提及』，实际政策文档里有——疑似召回失败"
}
```

## 4. 脱敏规则（硬性，不可跳过）

| 原始内容 | 替换为 |
| --- | --- |
| 客户/公司名 | `客户A`、`甲方B` |
| 人名 | `张某`、`李某` |
| 电话/账号/证号/合同号 | 整段删除或替换为 `<编号>` |
| 精确金额 | 保留数量级（如 "约 12 万"）或删除 |
| 内部系统名/项目代号 | 用 `内部系统X` 等代号，除非确需保留 |

**判断不了是否涉敏的内容，一律不收。** 宁可少十条，不要漏一条。

## 5. 提交方式

- 直接发我（表格/文本/JSON 均可，我来规范化），或按上面的字段填成 JSON。
- 每条尽量独立、单一事实；不要把三个问题合成一句。
- 拿不准的标签（`expected_route` / `expected_answer`）填 `unknown` 并在 `notes` 说明，
  交管理员确认——**不猜、不凑**。

## 6. 收到后的处理流程

1. 维护者去重、规范化、分配 `case_id` → 提交管理员确认标签。
2. 在固定知识库上**真实回放**：记录每次执行的轨迹、观测、聚类。
3. 产出带标签的真实观测集：诊断器结论 vs 已知标签对分，形成第 3 阶段验收依据。
4. 入库文件随提交记录可追溯；失败的案例**不得删除或改标签**来让报告好看。

## 7. 质量红线（对应设计门禁）

- 不得手写、篡改、补造任何执行结果或观测行。
- 不得为凑数量删除失败案例、修改期望标签或降低判定标准。
- 不得提交未脱敏内容。
- 整理范围仅限"问题与标签"；系统行为一律以真实回放为准。
