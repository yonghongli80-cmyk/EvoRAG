# 客服、销售与主播资料清洗指南

## 目的

把他人提供的资料转化为“可审核的候选知识”，而不是让人或模型直接修改原始话术。最终可发布知识由业务负责人确认；清洗人员只负责保留来源、找重复、找冲突和标风险。

## 绝对规则

1. 原始文件只读保存，不覆盖、不移动、不用模型改写后回存。
2. 不把全部 Excel、Word、PDF 合并成一个大 Markdown。
3. 不因文件名有“审核版”“最新”“最终版”就自动发布。
4. 不因两个问题语义相似就自动合并。
5. 不让模型判断售后、价格、运费、质保承诺是否真实。
6. 每个候选答案都必须能回到原文件、工作表和行号。

## 输出物

每次清洗生成独立批次，至少包含以下只读结果：

| 输出 | 内容 | 是否可直接对外回答 |
| --- | --- | --- |
| `source_manifest.csv` | 文件路径、哈希、更新时间、来源类别、导入批次 | 否 |
| `speech_candidates.xlsx` | 每行一条候选问答及完整来源 | 否 |
| `duplicate_clusters.xlsx` | 完全重复的来源行集合 | 否 |
| `conflicts_review.xlsx` | 同题异答及作用域差异 | 否 |
| `risk_review.xlsx` | 风险承诺、时间敏感、缺字段 | 否 |
| `cleaning_report.md` | 数量、错误、人工审核事项 | 否 |

发布后，系统中的 `published` 记录才可进入客服固定话术通道。

## 第 1 步：建立来源清单

为每个文件登记：

- 原始文件名和逻辑目录；不要登记或展示服务器物理路径。
- SHA-256、文件大小、修改时间、收到时间。
- 提供者和已知用途。
- 初始来源类别：`authoritative_candidate`、`reference`、`historical`、`personal_style`、`training`。

建议初始分类：

| 资料特征 | 初始类别 | 说明 |
| --- | --- | --- |
| 含“不能承诺、风险、审核、统一经营规则”列 | `authoritative_candidate` | 仍需负责人发布 |
| 普通标准话术库、分类话术表 | `reference` | 用于比对和候选导入 |
| 明确旧日期、旧规则或历史版本 | `historical` | 不默认对外回答 |
| 个人姓名话术、主播风格稿 | `personal_style` | 只能在明确人设/角色下使用 |
| 相机基础知识、品牌型号培训 | `training` | 进入 RAG 产品知识兜底 |

## 第 2 步：确定每张表的导入方式

不要按文件扩展名一刀切，按工作表内容选择：

| 表格特征 | 导入方式 | 例子 |
| --- | --- | --- |
| 有稳定的问题列和回答列 | `qa_pair` | 问题Q、标准回答A |
| 规则主题和统一口径 | `qa_pair` | 规则主题、统一口径 |
| 型号、参数、价格、库存等结构化数据 | `row_groups` + 结构化查询 | 型号清单、库存表 |
| 空表、封面、说明页 | 不索引或只做 schema 摘要 | 空 Sheet2/Sheet3 |
| Word/PDF 培训资料 | 普通文档切片 | 品牌知识、摄影基础 |

`qa_pair` 必须明确选择：表头行、数据起始行、问题列、回答列。可选映射分类、关键词、不能承诺、建议追问、转人工、品牌、型号、场景、角色、渠道、优先级、状态、版本、更新时间。

## 第 3 步：机械规范化

只修改“候选副本字段”，永远保留原始字段。

### 问题和回答文本

- Unicode NFKC 规范化。
- 全角空格、半角空格、换行统一；连续空白折叠成一个空格。
- 删除首尾空白。
- 统一常见中文标点，但保留原文版本。
- 空字符串标为缺失；不要把 `0`、`false`、`否`、`无`当作空。
- 不纠正业务词、不改型号、不删表情、不润色文案。

### 关键词

- 按 `、`、中文逗号、英文逗号、分号拆分。
- 去除空词、首尾空白、重复词。
- 保持原顺序；不要按模型猜测新增关键词。

### 作用域字段

为空时保持空，不擅自补“全品类”“全渠道”。

作用域包括：角色、渠道、人设、品类、品牌、型号、客户场景、地区、活动、有效时间。它们决定两条相同问题是否真的冲突。

## 第 4 步：重复、冲突与相似项

### 完全重复：可建议合并

同时满足以下条件才进入完全重复簇：

```text
规范化问题相同
规范化回答相同
角色、渠道、人设、品类、品牌、型号、场景、有效期相同
```

系统只合并“逻辑展示记录”，不删除任一来源行。

### 同题异答：必须审核

问题和作用域相同、回答不同，即使差异只是“7 天/365 天”“可/不可”“包运费/不包运费”，也必须进入待确认。系统不能选择最像、最新日期或字数最多的回答。

### 相似问题：只做建议

如“能退吗”和“七天无理由吗”语义接近，但不自动合并；可能一个问质量问题、一个问无理由退货，政策不同。

## 第 5 步：风险扫描

以下内容生成风险标记，供业务审核：

| 类别 | 常见信号 | 审核动作 |
| --- | --- | --- |
| 时间敏感 | 门店数、当天、48小时、近30天、7天、365天 | 确认日期、地域、活动条件 |
| 绝对承诺 | 100%、绝对、保证、完美、零风险、最低 | 确认真伪或改为合规表达 |
| 售后物流 | 包来回运费、无理由、保修、质保 | 确认品类、渠道、条件和例外 |
| 价格促销 | 最低价、降价、优惠、保价 | 确认时段、商品、渠道、库存 |
| 信息缺失 | “这款”“该商品”却无型号/链接/场景 | 增加追问或转人工 |
| 个人风格 | 姓名、主播口头禅、私域引流 | 限定角色和渠道 |

风险标记不等于删除。审核人必须写出：`发布`、`限定作用域发布`、`改写后发布`、`标记过期`或`停用`，以及原因。

## 第 6 步：人工审核与发布

审核时按以下顺序决策：

1. 先确认作用域是否相同。
2. 若作用域不同，分别发布并写清限制条件。
3. 若作用域相同且答案冲突，选择一个当前答案，其他标为 `superseded` 或 `disabled`。
4. 对风险承诺确认可用条件；不能确认时停用或要求改写。
5. 审核人填负责人、决定、理由、生效时间和复核日期。

推荐状态：

```text
candidate -> published
candidate -> disabled
published -> superseded
published -> disabled
```

任何状态变化都应保留审计，不覆盖原答案。

## 第 7 步：上线前抽检

每批至少抽检：

- 20 条已发布固定话术：回答、禁止承诺、建议追问、来源行是否正确。
- 10 组完全重复：确认没有误合并不同作用域。
- 全部同题异答：确认仍在待审核或已有明确决议。
- 全部风险承诺：确认有审核结论。
- 20 个真实客服问题：验证固定话术命中、澄清提问和 RAG 兜底。

未解决冲突不得由固定话术通道自动返回；系统应要求补充型号、渠道、场景，或提示转人工。

## 给 DeepSeek 的辅助提示词

DeepSeek 只能输出候选标签和差异说明，不能输出“最终正确答案”、不能改原文、不能删除记录。每次最多处理一个已脱敏批次，并要求 JSON 输出。

```text
你是企业话术资料的“只读审核助手”。

输入包含多条候选记录，每条包含：record_id、question_raw、answer_raw、category、brand、model、scene、audience、channel、source_file、sheet、row。

你的任务：
1. 判断两条记录是：exact_duplicate、same_question_different_scope、same_question_conflicting_answer、semantic_similar、unrelated。
2. 提取风险标签：time_sensitive、absolute_claim、price_claim、after_sales_claim、missing_scope、missing_answer。
3. 用不超过 80 字说明“为什么需要人工确认”。

硬性限制：
- 不得改写问题或答案。
- 不得决定哪条政策正确。
- 不得建议删除原始记录。
- 不得根据文件名、日期或语气自行认定“最新/审核版”必然正确。
- 作用域字段不同，默认 same_question_different_scope，除非存在直接矛盾。
- 无法判断时返回 needs_human_review。

只返回 JSON 数组，字段为：left_record_id、right_record_id、relation、risk_labels、reason、needs_human_review。
```
