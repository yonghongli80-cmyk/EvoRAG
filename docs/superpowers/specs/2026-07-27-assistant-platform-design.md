# RAGv3 场景助手平台、入职助手与制度助手设计

## 1. 目标

本阶段在现有 RAGv3 中增加配置化助手运行时，并交付入职助手和制度助手。

场景助手是同一聊天工作区的不同工作模式。它们共享账号、权限、知识库、文档版本、引用、反馈、收藏、历史和审计，不创建独立应用。

## 2. 单平台体验

用户登录后仍进入一个 RAGv3：

- 主导航保持文件、知识库、知识运营等统一入口。
- 首页显示用户有权限的助手快捷卡。
- 聊天页顶部提供助手选择器。
- 切换助手改变允许的知识范围、工具和输出模板。
- 对话历史记录当时使用的助手，但仍出现在同一个历史页面。

不为助手创建新的登录页、用户表、文件上传区、知识库副本或独立部署。

## 3. 助手配置

新增 `assistant_profiles`：

- `id` 和稳定 `key`。
- 名称、图标、说明。
- 启用状态和版本。
- 允许的知识库选择规则。
- 允许的工具集合。
- Workflow 类型。
- 系统指令模板。
- 输出 schema。
- 推荐问题。
- 所需能力。
- 负责人。
- 创建和更新时间。

配置只允许引用已有知识库和工具注册表，不能写任意 Python 导入路径。配置变更生成不可变版本，对话保存 `assistant_profile_version_id`，便于复现。

管理员负责启停，助手负责人维护知识范围、推荐问题和说明。负责人不能通过配置把自己无权访问的资料授予其他用户。

## 4. 运行时

统一入口：

```text
AssistantRequest
  user identity
  assistant profile version
  conversation
  question
      │
Capability + ACL gate
      │
Workflow runner
      ├─ retrieval tools
      ├─ comparison workflow
      ├─ structured-data gateway
      └─ deterministic business tools
      │
Evidence + answerability + citations
      │
same message/history/feedback pipeline
```

运行时支持三类执行方式：

- `rag_chat`：普通检索问答。
- `deterministic_workflow`：固定步骤、条件分支和工具调用。
- `controlled_multi_agent`：仅复杂比较或报告，具有最大步骤、时间和工具预算。

每次请求都创建不可变 `ExecutionContext`，包含用户 ID、能力、可见知识库、可见逻辑文档范围和请求 ID。模型和子任务只能缩小它，不能扩大。

## 5. 工具注册表

每个工具声明：

- 工具 key 和版本。
- 输入／输出 Pydantic schema。
- 所需能力。
- 允许的助手。
- 是否只读。
- 最大执行时间和结果大小。
- 是否允许外部模型看到输入和输出。
- 审计事件类型。

允许的工具示例：

- 权限安全检索。
- 文档比较。
- 版本引用打开。
- 结构化数据查询。
- 图表生成。
- 入职清单读写。
- 项目报告生成。

禁止助手直接使用文件路径、通用 shell、任意 SQL、任意 Python 或权限修改函数。

## 6. 多 Agent 边界

场景助手默认不是多 Agent。

允许的受控角色：

- `planner`：把复杂目标拆为有限子问题。
- `evidence_worker`：调用指定范围的只读工具。
- `verifier`：检查引用覆盖、冲突和输出 schema。

限制：

- 最大 3 类角色。
- 最大可配置步骤和并行数。
- 所有角色共享同一 ExecutionContext。
- 角色之间只传结构化证据和安全摘要。
- 不允许自主新建角色或修改工具集合。
- 失败时返回部分证据和失败项，不无限自我反思。

## 7. 入职助手

### 7.1 目标

帮助新员工了解第一天、第一周和第一个月需要完成的事项，并快速找到制度和联系人。

### 7.2 数据

- 入职指南和流程。
- 常见制度。
- 部门公开说明。
- 办公系统使用说明。
- 培训资料。
- 负责人维护的联系人和链接。

第一版不读取工资、身份证、合同、体检、处分或个人档案。

### 7.3 能力

- 按阶段展示入职清单。
- 回答流程问题并引用当前文件。
- 推荐下一项。
- 标记个人完成状态。
- 对无法回答的问题提交反馈。

清单完成状态是个人工作记录，不代表 HR 正式审批结果。外部系统事项只提供链接和说明，不伪造“已开通”“已审批”状态。

### 7.4 错误边界

- 制度与入职指南冲突：显示冲突并优先引用当前制度，不自动决定。
- 联系人资料过期：创建负责人待办。
- 用户没有某部门资料权限：不显示该步骤中的受限内容。

## 8. 制度助手

### 8.1 目标

面向公司制度、流程和规范提供可靠问答、比较和有效性判断。

### 8.2 检索

- 默认只使用当前有效版本。
- 按适用范围、部门、地区和生效日期过滤。
- 历史版本只在用户明确要求历史或当前证据不足时使用，并显示警告。
- 同主题制度冲突时调用阶段 1 的冲突服务。

### 8.3 能力

- 制度问答。
- 两份或多份制度比较。
- 新旧版本变化说明。
- 适用范围解释。
- 无答案和冲突上报。

“适用于我吗”第一版只能根据用户主动选择的部门／地区或已有可靠属性判断。组织属性未接入时不得猜测用户所属范围。

### 8.4 输出

- 结论。
- 适用范围。
- 生效日期。
- 置信度和理由。
- 当前引用。
- 历史或冲突警告。
- 原文打开入口。

制度助手不提供法律意见，不把模型结论标记为人事或法务批准。

## 9. UI

助手卡片包含：

- 名称和说明。
- 负责人。
- 最近更新时间。
- 推荐问题。
- 是否需要额外能力。

聊天页切换助手时：

- 新建或明确切换对话上下文。
- 不把上一个助手的隐藏系统指令和工具状态带入。
- 可以引用同一用户有权访问的历史消息，但必须重新校验关联资源。

助手管理位于设置或知识运营的管理员区域，不增加主导航一级页面。

## 10. API

建议：

- `GET /assistants`
- `GET /assistants/{key}`
- `POST /assistants/{key}/conversations`
- `POST /assistants/{key}/query`
- `POST /assistants/{key}/query/stream`
- `GET/POST/PUT /admin/assistants`
- `POST /admin/assistants/{id}/publish`
- `GET/PUT /onboarding/checklist`

现有普通聊天 API 继续工作。助手流式响应复用 assistant message ID、citation、reliability 和 feedback 协议。

## 11. 配置发布

配置编辑分为草稿和发布版本：

1. 编辑草稿。
2. 验证知识库、工具、能力和输出 schema。
3. 使用固定测试集试运行。
4. 发布不可变版本。
5. 新对话使用新版，已开始对话继续记录原版本或明确提示切换。

停用助手不删除历史消息。用户打开旧对话时可查看已有内容，但重新提问要求选择可用助手。

## 12. 失败与降级

- 助手配置无效：禁止发布。
- 某工具不可用：如果不是必需工具则降级并提示；必需工具失败则停止。
- 多 Agent 超预算：返回已收集证据和未完成步骤。
- 输出 schema 校验失败：最多一次受控修复，再返回稳定错误。
- 助手知识库被删除：标记配置失效并通知负责人。
- 用户能力变化：下一次请求即时生效。

## 13. 测试

必须覆盖：

- 五类助手未来都使用同一账号和对话数据模型。
- 助手切换不能扩大 ACL。
- 配置不能引用任意代码或未注册工具。
- 配置版本能复现旧对话。
- 子角色无法修改 ExecutionContext。
- 多 Agent 步数、时间和并发限制生效。
- 入职助手不读取个人 HR 数据。
- 入职清单与正式审批状态明确区分。
- 制度助手默认只引用当前有效版。
- 冲突制度不生成无警告结论。
- 停用助手后历史可读但不能继续执行。
- 流式响应继续保存引用、可靠性和反馈关联。

## 14. 完成标准

- 用户只感知一个 RAGv3 平台。
- 新助手通过配置和 Workflow 增加，不复制底层系统。
- 入职和制度助手的所有结论遵守当前权限与引用规则。
- 复杂任务可以受控并行，普通任务不承担多 Agent 成本。
