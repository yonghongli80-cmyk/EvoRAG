# RAGv3 企业治理设计

## 1. 目标

本阶段让 RAGv3 能在约 400 人规模下回答五个问题：

1. 谁被允许做什么。
2. 谁实际做过什么。
3. 敏感资料如何识别和限制。
4. 数据损坏后如何恢复。
5. 员工离职后知识资产如何连续。

治理能力仍属于同一平台，不创建独立的“安全后台”产品。

## 2. 范围

包含：

- 职责分离和能力权限。
- 文件敏感等级与检测建议。
- 审计事件、检索和防篡改链。
- 批量权限变更、预览和撤销。
- 备份、校验、恢复演练。
- 离职停用和资产交接。
- 临时授权和到期回收。

不包含：

- 钉钉组织同步。
- 部门、岗位、上下级自动继承。
- 法务或合规认证结论。
- DLP 客户端、终端水印或屏幕防截取。
- 真实工资、考勤启用审批；该决定由主管在部署前完成。

## 3. 职责与能力

系统不再用单一 `is_admin` 表达所有高权限职责。新增可组合能力：

- `platform_admin`：账号、配置、服务状态和权限策略。
- `content_admin`：知识库和文档运营，不自动读取严格受限正文。
- `auditor`：查看审计事件和策略结果，不读取业务正文。
- `backup_operator`：执行备份、校验和恢复，不浏览文档内容。
- `hr_data_analyst`：查询被授权的工资、考勤结构化数据。
- `permission_operator`：执行已审批的批量权限变更。
- `handover_operator`：执行账号停用和资产交接。

能力通过用户或本地用户组授予。一个人可以兼任，但每项能力必须显式存在。

兼容策略：

- 迁移后现有管理员获得 `platform_admin` 和 `content_admin`。
- 不自动获得 `hr_data_analyst`。
- 审计、备份和离职操作仍需对应能力。
- 前端隐藏入口只是体验优化，后端每个 API 都独立校验能力。

## 4. 敏感分级

### 4.1 等级

- `internal`：普通内部资料。
- `confidential`：客户、合同、经营、项目等受限资料。
- `restricted`：工资、考勤、身份证件、健康、人事处分等严格受限资料。

等级绑定逻辑文档，版本继承。新版本可以提高敏感等级；降低等级必须由文件负责人和具备 `content_admin` 的人员确认。

### 4.2 检测

上传后异步扫描：

- 文件名和表头模式。
- 身份证、手机号、银行卡等格式。
- 工资、奖金、考勤、处分等敏感词。
- 单元格密度和疑似个人记录列。

检测结果是建议，不自动授予或撤销权限。高风险命中时文件进入 `classification_pending`，完成分类前只允许上传者和具备相应能力者访问。

新文件先进入本地隔离区。本地沙箱解析可以用于检查文件名、表头和内容模式，但 `classification_pending` 期间禁止外部嵌入、外部 LLM、Qdrant 写入、普通预览、下载和搜索。分类确认并匹配策略后才允许后续索引。

### 4.3 模型策略

每个敏感等级配置：

- 是否允许外部模型。
- 是否允许嵌入服务。
- 是否允许返回明细。
- 是否允许导出。
- 是否允许生成图表。

工资、考勤初始策略为生产关闭。主管批准后才能改变，配置变化写入审计。

## 5. 审计

### 5.1 事件范围

记录：

- 登录、退出、失败登录和会话撤销。
- 搜索、问答、比较、结构化查询。
- 引用打开、文件下载和结果导出。
- 上传、覆盖、删除和恢复版本。
- 分享、撤权、负责人变化和批量权限。
- 敏感等级变化。
- 任务处理和冲突确认。
- 备份、校验、恢复和离职交接。
- 助手配置启停和高风险工具调用。

### 5.2 事件结构

每条事件包含：

- 事件 ID、时间、actor ID。
- 动作、资源类型和逻辑资源 ID。
- 成功／失败和稳定错误码。
- 会话、请求和关联事件 ID。
- 权限决策结果和使用能力。
- 客户端 IP 的规范化表示。
- 非敏感参数摘要。
- 前一事件哈希和当前事件哈希。

不记录密码、令牌、完整问题正文、工资明细、物理路径和外部服务密钥。需要调查内容时通过原始业务记录的权限 API 获取，不把内容复制进审计库。

### 5.3 防篡改

审计表只追加。应用账号没有 UPDATE/DELETE 路径。事件按批次生成哈希链和签名清单；每日校验并报告断链。

`platform_admin` 不能删除审计事件。保留期和归档由部署配置决定，清理只能执行“签名归档后删除在线副本”的运维流程。

## 6. 批量权限

批量操作输入：

- 目标用户或本地用户组。
- 目标知识库／文件集合。
- view／edit 权限。
- 生效和到期时间。
- 业务理由。

执行流程：

1. 生成预览，不修改数据。
2. 显示新增、覆盖、跳过、冲突和受限资源数量。
3. 操作者确认。
4. 为本次操作创建批次 ID。
5. 逐项幂等执行并记录原状态。
6. 生成结果和失败清单。

撤销只恢复该批次实际改变且之后未被其他操作修改的条目；发生后续修改时标记冲突，不能粗暴覆盖。

严格受限资料不能通过普通批量分享获得访问权，必须使用对应能力和独立操作。

## 7. 临时访问

权限可以设置 `valid_from` 和 `expires_at`。过期由后端查询时即时判定，后台任务负责清理和通知，不能依赖后台任务及时运行才阻止访问。

紧急访问必须填写理由和截止时间，单独标记审计事件。第一版不做多级审批，但保留 `approval_ref` 字段。

## 8. 备份与恢复

### 8.1 备份集合

一次一致性备份在全局写屏障下生成同一 `backup_epoch`，包含：

- SQLite 数据库快照。
- 不可变文档版本。
- Qdrant collection 快照或可重建清单。
- 配置清单和 schema 版本。
- 文件哈希、数量和尺寸。

密钥不与备份数据打包；只记录密钥版本标识。备份文件加密，备份操作者不能通过管理页面直接预览正文。

写屏障期间排空活动写入，执行 SQLite `wal_checkpoint(FULL)` 并通过 SQLite backup API 取快照，不直接复制活动中的 WAL 文件；再复制不可变文件/结构化库，请求 Qdrant snapshot 并等待完成。签名清单把同一 `backup_epoch`、SQLite mutation sequence、文件哈希和 Qdrant snapshot ID 绑定为一个恢复点；任一组件失败都不得发布 `restorable` 清单，第一版不接受跨清单或跨 epoch 拼装恢复。

### 8.2 状态

- `created`
- `verified`
- `verification_failed`
- `restore_testing`
- `restorable`
- `expired`

只有通过哈希、SQLite integrity check、文件清单和 Qdrant 对应校验的备份才标记 `restorable`。

### 8.3 恢复

恢复先进入隔离目录和临时数据库：

1. 验证备份签名和清单。
2. 执行 schema 迁移预检。
3. 抽样验证文档版本和引用。
4. 验证向量快照或执行隔离重建。
5. 生成恢复报告。
6. 经明确确认后切换生产指针。

恢复失败不能改动当前生产状态。每季度至少执行一次自动化恢复演练。

## 9. 离职交接

离职流程是一个可重试的状态机：

- `planned`
- `account_disabled`
- `sessions_revoked`
- `assets_assigned`
- `verified`
- `completed`
- `failed`

流程：

1. 选择离职用户和接收人。
2. 预览其负责文档、知识库、任务、订阅和共享权限。
3. 停用账号并撤销所有会话。
4. 撤销其被授予的访问权限和临时授权。
5. 转移负责人、未完成任务和必要订阅。
6. 保留历史上传者、消息、反馈和审计 actor。
7. 验证不存在 `owner_id` 指向已停用且无接收人的活动资源。

离职交接不删除原用户记录，也不把历史行为改写成接收人的行为。流程中断后从已完成状态继续，不重复转移。

## 10. API 与页面

知识运营页面增加管理员可见的治理入口：

- 权限能力。
- 敏感分类待确认。
- 批量权限。
- 审计检索。
- 备份与恢复。
- 离职交接。

建议 API：

- `GET/PUT /governance/users/{user_id}/capabilities`
- `GET/PUT /documents/{document_id}/classification`
- `POST /permission-batches/preview`
- `POST /permission-batches`
- `POST /permission-batches/{batch_id}/rollback`
- `GET /audit-events`
- `POST /backups`
- `POST /backups/{backup_id}/verify`
- `POST /backups/{backup_id}/restore-test`
- `POST /handovers/preview`
- `POST /handovers`
- `GET /handovers/{handover_id}`

所有列表分页并使用稳定筛选字段。错误响应不包含数据路径或内部异常。

## 11. 失败处理

- 敏感扫描失败：保持待确认，不降级为普通文件。
- 审计写入失败：高风险变更失败关闭；普通只读查询按策略记录告警并可失败关闭。
- 批量权限部分失败：保留逐项结果，可用同一幂等键重试失败项。
- 备份校验失败：不得用于恢复。
- 交接接收人被停用：中止交接，不自动选择其他人。
- 会话撤销失败：账号保持停用，持续重试撤销。

## 12. 测试

必须覆盖：

- 系统管理员没有 HR 能力时看不到工资明文。
- 审计员和备份管理员不能借入口下载业务文件。
- 权限能力的前端隐藏和后端拒绝一致。
- 敏感等级降低要求额外确认。
- 分类失败不开放文件。
- 审计事件哈希链可验证，篡改单条后校验失败。
- 批量预览与实际结果一致。
- 批次撤销不覆盖后续人工修改。
- 临时权限到期后即时拒绝。
- 备份缺文件、哈希错误或数据库损坏时不可恢复。
- 恢复测试不修改生产数据。
- 离职流程幂等，历史 actor 不被改写。
- 已停用用户无法使用旧会话。

## 13. 完成标准

- 管理职责和业务数据读取权明确分离。
- 所有高风险动作可追溯且普通管理员不能消除痕迹。
- 备份存在不等于成功；系统能给出已验证可恢复证据。
- 离职后没有活动资源失去负责人，也没有旧会话继续访问。
- 真实工资、考勤在主管确认前保持生产关闭。
