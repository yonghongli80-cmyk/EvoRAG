# 人工主导的知识库自进化系统设计

## 1. 目标与定位

本系统用于帮助管理员快速处理知识库建设初期反复出现的文档、表格、切块、检索、字段映射和工作流适配问题。它不是自治发布者，而是后台运行的诊断、候选修复和验证助手。

人工始终拥有最高控制权：人工决定问题是否值得处理、确认或修订根因、批准生成候选、核验演示和证据、批准灰度与稳定发布，并可随时回退。任何候选都不得绕过人工确认进入稳定版本。

系统必须与在线应用解耦。后台自进化停机、超时或失败时，主应用继续使用当前稳定版本提供服务。

## 2. 范围与阶段

首期不实现 Jev 的具体问题和 SDK 接入，但必须预留统一 Jev 兼容协议。项目实施顺序为：

1. 先建设 Jev 快速决策层，解决当前链路速度和未来规则增长问题。
2. 再建设本设计描述的后台自进化闭环。
3. 自进化生成的新路由、判断和规则通过版本化协议交给 Jev 在线执行。

自进化允许修改的范围分阶段开放：

1. 提示词、检索配置、查询改写、字段映射和知识库适配规则。
2. 切块策略、重排流程、解析器和工具工作流。
3. 项目代码，但只能在隔离 Git worktree 中形成候选补丁。

权限策略、审计记录、验收器、测试基准、发布门禁、密钥和用户原始数据永久禁止由进化任务修改。白名单扩大必须由管理员操作并留下审计记录。

## 3. 在线快链路与后台慢链路

在线链路只执行提问、快速判断、检索或结构化查询、回答和轻量轨迹记录。它不等待诊断、候选生成或回归测试。

后台链路采用独立任务队列、进程或容器、数据表、产物存储和 Git worktree。默认白天低优先级归档与聚类，每天夜间批量分析；管理员可手动触发。后台任务限制 CPU、内存、并发、模型预算和运行时间，系统繁忙时暂停，空闲后恢复。

推荐采用混合探索模式：日常问题生成一个最小候选；重复失败、影响较大或单候选连续失败时，启动 DGM 式多分支探索。低分候选可保留在探索档案，但不能进入稳定发布列表。

## 4. Jev 兼容边界

Jev 是未来在线快链路的结构化决策层，自进化是慢速学习层。二者共享以下稳定协议：

- `state`：问题、知识库类型、权限过滤后的候选摘要、会话状态和必要业务事实。
- `questions`：稳定 ID、版本、Choice/Score/Noul 类型、指令和判定标准。
- `answers`：结果、概率分布、置信度、模型版本和耗时。
- `policy`：阈值、组合权重、降级策略和允许动作。
- `trace`：实际使用的判断、路由依据及最终效果。

自进化只能生成版本化的 Jev 问题集和策略候选。候选必须通过历史轨迹回放、置信度校准、延迟和成本评测，并经人工核验和指定知识库灰度后才能晋升。普通代码继续负责权限、文件存在性、精确计算和确定性规则。

## 5. 失败准入与聚类

以下情况不进入进化：权限不足、文件不存在、用户问题含糊，以及外部模型、网络或服务的临时故障。

- 单次偶发失败、缺少可靠参考或无法稳定复现：进入观察队列。
- 同类根因累计三次：自动进入候选池。
- 管理员明确标记或高风险错误：不受次数限制。
- 错误答案有充分证据、精确计算错误、引用与原文矛盾或安全边界异常：提高优先级。

在线服务只记录权限过滤后的可诊断轨迹，包括问题、路由、查询改写、候选块、排序分数、采用证据、工具调用、结构化查询、异常、最终回答、可靠性判断、反馈及相关版本。

## 6. 参考证据与诊断

参考依据按以下优先级构造：

1. 数据库结果、表格精确查询、程序测试等确定性证据。
2. 管理员确认的正确答案和历史成功轨迹。
3. 原始文档引用和多个独立模型一致结论。

诊断模型比较失败轨迹和参考轨迹，定位第一处实质偏离，并输出固定结构：失败类别、发生阶段、第一处偏离、直接证据、根因、影响范围、建议修改层级、复现方法和验收标准。

根因包括意图或路由错误、查询改写丢失信息、召回遗漏、块排序错误、切块破坏结构、工具选择或参数错误、结构化查询规划错误、生成器未利用证据、证据冲突未识别、提示词或工作流缺陷、代码缺陷及无法确定。

没有可重复复现、没有确切证据或根因仍为“无法确定”的任务只能留在观察队列，不能进入自动修改阶段。

## 7. 组件与状态机

系统由六个边界清晰的组件构成：

- `FailureRecorder`：在线请求结束后异步记录轨迹。
- `FailureClusterer`：按知识库、失败阶段和根因特征聚类。
- `EvolutionDiagnoser`：生成参考轨迹对比和结构化诊断草案。
- `CandidateBuilder`：在隔离环境中生成最小候选修改。
- `EvidenceRunner`：重放失败案例、运行回归并生成演示和证据包。
- `ReleaseManager`：处理审批、知识库级灰度、晋升和回退。

主要状态为：

`observed → clustered → awaiting_diagnosis_review → approved_for_candidate → candidate_testing → awaiting_verification → approved_for_canary → canary → stable`

任意阶段都可进入 `rejected`、`blocked`、`needs_more_evidence` 或 `rolled_back`。进化任务失败只改变自身状态，不改变在线稳定版本。

## 8. 人工核验与证据包

“知识运营”下新增“进化中心”，包含问题观察、诊断审核、候选核验和版本管理。

每个候选自动生成核验包：

- 原始失败问题、失败轨迹和复现步骤。
- 根因分类、第一处偏离和直接证据。
- 修复前后可重复演示。
- 引用、精确计算、测试或管理员认可答案。
- 文件、配置和行为差异。
- 新增回归测试和完整门禁报告。
- 准确率、延迟、Token、费用和资源变化。
- 权限与安全影响。
- Git 提交、版本号和回退点。
- 管理员批准、拒绝及备注记录。

管理员必须重新运行原始案例、核验证据、检查旧能力回归和修改范围，并填写批准说明后，候选才能进入灰度。

## 9. 门禁与禁止条件

候选依次通过五层门禁：

1. 证据门：问题可复现，修复结果有可追踪证据。
2. 功能门：原始失败和同类扩展案例通过。
3. 回归门：权限、文件访问、普通 RAG、结构化表格查询等关键能力不退化。
4. 工程门：类型、单元、集成、复杂度、重复代码、依赖和安全检查通过。
5. 资源门：延迟、Token、费用、CPU 和存储在预算内。

修改权限或审计边界、修改验收器、删除失败测试、硬编码具体答案、无法复现、证据不可追踪、关键能力回归或没有可靠回退点，均为硬性否决项。

## 10. 灰度、稳定发布与回退

发布采用按知识库灰度和双重人工确认：管理员先批准进入指定知识库灰度，观察期结束后再次确认才能成为稳定版本。

每个不可变版本快照绑定 Git 提交，并保存提示词、检索参数、切块策略、解析规则、Jev 问题集及索引版本。回退通过切换到上一稳定快照完成，不在现场反向编辑文件。涉及重新切块或索引时，旧索引保留至观察期结束。回退需记录操作人、原因和影响范围。

## 11. 评测指标

系统分别记录问题解决率、同类问题泛化率、错误答案率、拒答准确率、引用正确率、结构化计算准确率、旧能力回归数、平均延迟、请求与候选成本、人工核验通过率及灰度回退率。总分提升不能抵消任何安全、权限或关键能力硬性回归。

## 12. 实施阶段

1. 先单独完成 Jev 快速决策层设计与实现。
2. 建设观测基础：失败轨迹、分类、后台队列、聚类和管理页面。
3. 建设诊断辅助：参考证据、轨迹对比、根因草案和人工确认。
4. 开放低风险候选：提示词、检索参数、字段映射和适配规则。
5. 开放隔离代码进化：worktree、多候选探索、完整门禁、知识库级灰度和快照回退。

本设计借鉴 HarnessEvolve 的参考轨迹和门控、DGM 的多分支探索和版本谱系，但增加生产所需的人工优先、权限隔离、工程质量、可演示证据、灰度与回退约束。
