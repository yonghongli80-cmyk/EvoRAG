# 组织架构知识库鉴权升级设计

日期：2026-08-20  
状态：设计已确认，待实施计划

## 1. 目标与设计边界

本设计在当前 RAGv3 项目内升级身份、组织和知识库鉴权，使固定的虚构组织成员可以使用各自账号登录，并且只能看到、检索和操作其组织权限允许的知识库。

本设计只改造“知识库”权限域，不合并两套权限模型：

- **文件页面**继续使用现有个人所有权以及“私密、共享、公开”三级权限；
- **知识库页面**改用组织所有权、负责人管辖范围和敏感资格；
- 知识库内文件完全继承所在知识库的权限，不能另设个人私密或个人共享；
- 文件页面中的个人文件不会因为同一用户拥有知识库权限而改变可见范围，反之亦然。

本文档就“在当前 RAGv3 实施组织鉴权”这一范围，取代 `2026-08-12-organizational-nas-knowledge-base-design.md` 中“禁止直接在 RAGv3 实施、另建项目”的边界。旧文档中的 NAS、钉钉和真实公司名单不在本次范围内，后续若需要必须单独设计。

## 2. 已选择方案

采用“固定虚构组织 + 确定性初始化”的方案：组织、人员、账号、职位、负责人关系、敏感资格、知识库和示例资料均由受版本控制的固定数据定义。

没有采用以下方案：

- **每次随机生成数据**：不利于复现权限问题和编写稳定测试；
- **复制后改名真实组织数据**：可能残留真实关系或身份信息，也难以证明已经完全匿名化；
- **继续复用知识库 private/shared/public**：个人可以改变部门资产可见性，与组织所有权冲突。

固定数据方案可以稳定复现任意账号的权限，适合当前本地部署和后续自动化回归。

## 3. 双权限域架构

系统必须把文件权限和知识库权限作为两个独立域：

```text
文件页面 -> 用户所有权 + private/shared/public + 原有个人分享
知识库页 -> 组织归属 + 负责人范围 + 敏感资格 + 管理员特别授权
```

知识库不能由个人所有。`created_by` 只记录创建者，不代表所有权。知识库唯一业务所有者是组织节点；公司公共库和敏感库也必须保存明确的组织归属与类型。

知识库权限解析统一返回以下有效角色：

- `none`：资源不可见；
- `read`：列表、详情、预览、问答、检索和下载；
- `manage`：包含 `read`，并可上传、更新和删除知识库内资料；
- `administer`：包含 `manage`，并可改变组织归属、知识库类型、敏感域和特别授权，仅公司管理员拥有。

普通员工不能创建知识库。负责人可以在其管辖的组织范围内创建普通组织知识库，创建后只能管理内容，不能改变归属或敏感属性。公司管理员可以创建和管理所有类型知识库。

## 4. 身份、人员和组织模型

现有 `users.id` 继续作为认证主体和 JWT 内部身份。姓名不能用于登录匹配、授权或自动绑定。

组织子系统至少包含以下概念：

- `org_units`：稳定组织编号、父组织、显示名称、层级类型、启用状态；
- `org_people`：稳定人员编号、对应 `user_id`、显示姓名、职位、任职状态；
- `org_memberships`：人员所属组织、主部门标记和兼职标记；
- `org_manager_scopes`：负责人及其管理起点，默认向所有启用的后代节点继承；
- `org_sensitive_qualifications`：人员具备的财务、人事或客户敏感资格；
- `user_security_versions`：账号安全版本，用于停用账号、调岗或关键授权变更后使旧令牌失效。

组织编号、人员编号和账号都是稳定键；姓名、职位和部门名称只是显示字段，可以改名而不改变授权关系。

同一人员可有一个主部门和多个兼职部门。普通读取权限合并全部有效成员关系；负责人管理权只来自明确的负责人范围，兼职身份不会自动获得管理权。

账号停用、人员离职、关键组织关系变更或安全版本变化后，后端在每次受保护请求中拒绝旧令牌。只在前端清除登录状态不满足此要求。

## 5. 固定虚构数据

初始化清单采用固定、可审计的数据，并满足以下规模：

- 61 个组织节点，包含公司、事业群、中心、部门和工作组，最大四级；
- 280 名可登录员工；
- 49 名不同层级负责人；
- 8 名跨部门兼职人员；
- 2 名公司管理员；
- 财务、人事、客户三类敏感资格；
- 65 个知识库：1 个公司公共库、61 个组织节点库和 3 个敏感库；
- 每个知识库包含 1 至 2 份固定的虚构示例资料，用于验证浏览、检索、问答和下载。

所有姓名、职位、部门、文档标题和正文均为新编虚构内容，不复制参考项目的真实文本。初始化数据必须经过禁止词扫描，防止残留参考项目中的真实公司名、部门名、姓名或职位名。

登录账号固定为 `demo001` 至 `demo280`，每个账号与一名员工一一对应。账号对应关系在重新初始化后不能变化。例如，一个固定记录同时保存账号、员工姓名、职位、主部门、兼职部门和负责人范围。

初始密码统一为 `123456`，不强制修改。登录页、用户信息区和知识库页面不显示“演示环境”“测试账号”或类似标注。

初始化必须幂等：重复执行只能补齐缺失的系统种子数据，不能重复创建，也不能覆盖管理员或用户在首次初始化后的正常修改。种子记录使用稳定业务键和种子版本识别，初始化结果必须核对上述数量及引用完整性。

## 6. 知识库归属与授权规则

知识库保存稳定的组织归属和类型：

- `company_public`：所有启用员工可读；
- `organization`：所属组织成员可读，负责人按管辖树管理；
- `sensitive`：必须同时满足组织范围与对应敏感资格；
- `unassigned`：迁移期间的旧知识库，仅公司管理员可见。

敏感资格是额外门槛，不是独立放行条件。只有敏感资格但不在允许组织范围内，或者只有组织关系但没有敏感资格，均不得访问敏感库。

公司管理员可以配置跨组织特别授权。特别授权面向稳定用户或组织主体，角色只能为 `read` 或 `manage`，并可设置显式 `deny`。同一请求中，有效 `deny` 高于管理员之外的成员、负责人和特别允许规则。公司管理员自身仍保留灾难恢复所需的 `administer` 权限，但所有管理员操作都写入审计。

组织停用后，其普通知识库进入仅公司管理员可见状态，不删除任何资料。员工调岗后按新的有效成员关系实时计算权限，不保留旧部门访问权。负责人撤销后失去管理权，但仍保留其作为普通成员应有的读取权。

## 7. 旧知识库迁移

升级不得删除、猜测或自动公开现有知识库：

1. 为现有知识库建立组织权限记录并标记为 `unassigned`；
2. 迁移期间仅公司管理员可以看到和操作这些知识库；
3. 管理员明确选择组织归属和类型后，知识库才按新规则开放；
4. 旧知识库的 private/shared/public 和个人分享信息只保留为迁移审计数据，不再参与知识库授权；
5. 旧知识库内全部资料自动继承新的知识库权限。

迁移必须可重复、可中断后继续，并记录每个知识库的迁移前状态、迁移结果和操作者。文件页面的原有权限表与数据不得由本迁移改写。

## 8. 统一后端鉴权

前端隐藏按钮只用于改善操作体验，不能承担安全职责。知识库列表、详情、资料列表、预览、下载、上传、更新、删除、搜索、问答和管理接口必须调用同一个知识库授权服务。

授权服务的输入至少为 `user_id + knowledge_base_id + required_role`，输出允许或拒绝及内部 reason code。所有知识库入口必须使用它，不能在不同 API 内复制条件判断。

检索必须先获得当前用户可访问的知识库或文档集合，再将范围下推到向量检索、BM25、材料检索和问答引用链。禁止先做全库召回、生成摘要或答案后再过滤。空授权集合直接返回空结果；ACL 解析或过滤失败时 fail closed，不退回全库检索。

无权访问的资源对外表现为不存在或空结果，不能泄露知识库名称、文档标题、命中数量、摘要、正文、路径或敏感类型。手工构造 ID、旧链接、引用重开和下载地址必须得到相同结果。

文件页面继续调用原有个人文件权限服务。知识库授权服务不得更改文件页面 private/shared/public 的语义。

## 9. 前端交互

### 9.1 登录与人员信息

登录仍使用账号和密码。增加账号选择入口，可以按固定员工姓名、编号、部门和职位筛选；选择员工后填入对应账号。密码仍由用户输入或按现有登录体验处理，不在页面中公开展示密码。

登录后显示姓名、人员编号、职位、主部门和兼职部门，但不显示“演示”“测试”等环境标签。

### 9.2 知识库页面

知识库页面只渲染后端返回的有权知识库，并按公司公共库、组织库和敏感库分区。知识库卡片显示名称、所属组织、类型以及当前账号的“可查看”“可管理”状态。

知识库页面移除 private/shared/public 和个人分享控件。普通员工不显示创建入口；负责人只能在其管辖范围内选择组织并创建普通组织知识库；公司管理员拥有完整入口。

### 9.3 组织权限管理

新增组织权限管理界面：左侧展示四级组织树，右侧展示人员、负责人、兼职关系、敏感资格和所属知识库。

公司管理员可以调整人员组织、负责人、兼职、账号状态、敏感资格、知识库归属和特别授权。普通负责人只能读取其管辖范围内的组织信息，不能修改组织架构。

管理员可以使用“以此账号查看”预览某位员工可见的知识库集合。该功能只展示权限计算结果，不签发被预览员工的会话，也不能代替该员工执行写操作。

### 9.4 文件页面

文件页面保留现有布局和私密、共享、公开三级权限。必要时只增加“个人文件权限”文字说明，以避免与组织知识库权限混淆，不改变原有功能。

## 10. 审计与异常处理

必须记录以下事件：

- 登录成功、登录失败、账号停用和令牌失效；
- 人员调岗、兼职变更、负责人变化和敏感资格变化；
- 知识库创建、归属调整、类型或敏感域调整、特别授权与撤权；
- 资料上传、下载、更新、删除、问答以及被拒绝的越权访问。

审计记录包含操作者、时间、内部目标 ID、动作、结果和 reason code，不记录密码、令牌、文档正文或敏感查询正文。公司管理员可查看全部审计；负责人只能查看其管辖范围内的非安全敏感操作记录。

组织引用缺失、组织树成环、重复账号、重复人员编号、无效负责人范围或无效敏感域必须使初始化或管理事务失败，不能部分保存。数据库写入继续遵守现有 `UserDB` 锁和事务边界，避免重新引入 SQLite 并发锁问题。

## 11. TDD 与验收标准

实施必须遵循严格 TDD：每个行为先编写能够证明缺失或错误的失败测试，再写最少实现使其通过，随后重构并重新运行相关测试。每一阶段形成独立、可回退的提交。

最低验收范围如下：

1. 280 个固定账号均能以对应账号和初始密码登录，姓名、编号、职位和部门映射稳定；
2. 普通员工、组负责人、部门负责人、事业群负责人和公司管理员的权限矩阵符合设计；
3. 8 名兼职人员的普通权限正确合并，但不会凭兼职身份获得负责人权限；
4. 财务、人事和客户三类敏感库同时验证“有组织无资格”“有资格无组织”“两者都有”三种情况；
5. 列表、详情、预览、下载、上传、删除、搜索、问答、引用重开和手工构造地址均无法越权；
6. 知识库不能被个人设为私密、公开或个人共享，知识库内文件不能脱离知识库单独授权；
7. 文件页面 private/shared/public 及个人分享的现有测试全部回归通过；
8. 旧知识库迁移后默认仅管理员可见，明确归属后才对目标组织开放；
9. 重复初始化不会产生重复组织、人员、账号、关系、知识库或示例资料，也不会覆盖初始化后的合法修改；
10. 调岗、离职、负责人撤销、组织停用和账号停用能够立即影响后端请求，包括已签发令牌；
11. 越权响应不泄露资源是否存在，审计记录完整且不包含密钥或正文；
12. 全量后端测试、前端测试和生产构建通过，才可以宣告完成。

## 12. 分阶段交付

为控制风险，实施计划应按以下顺序拆分：

1. 固定组织数据、身份扩展、数据库迁移和幂等初始化；
2. 纯函数式权限计算器及完整权限矩阵；
3. 知识库数据迁移和统一后端鉴权服务；
4. 检索、问答、预览、下载和引用链的前置过滤；
5. 登录账号选择、知识库页和组织权限管理界面；
6. 审计、令牌失效、全量回归与生产构建。

每一阶段都必须保持文件页面原有权限可用。若某阶段不能安全迁移旧数据或不能 fail closed，应停止发布，而不是临时放宽权限。

## 13. 明确不在本次范围内

- 不接入真实公司员工、部门、姓名或职位数据；
- 不接入钉钉、LDAP、企业微信或其他单点登录；
- 不接入 NAS，也不改变现有备份策略；
- 不强制首次登录修改密码；
- 不把文件页面改造成组织权限；
- 不允许个人拥有、私密化或任意分享组织知识库；
- 不因本次改造删除旧知识库或旧文件。
