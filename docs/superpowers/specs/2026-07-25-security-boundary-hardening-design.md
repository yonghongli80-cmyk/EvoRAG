# RAGv3 安全边界收敛设计

## 1. 目标

本阶段只修复当前 RAGv3 已确认的安全与数据一致性问题，为后续企业权限和 NAS 接入建立可信底座。NAS、钉钉、部门岗位、400 人批量导入不在本阶段实现范围内。

完成后必须满足：

- 未认证用户不能上传、下载、索引、查询或管理知识库内容。
- 所有知识库和文档读写都通过同一套服务端权限校验。
- `shared` 知识库只对所有者、管理员和明确的共享对象可见。
- 私有内容不会通过静态文件、检索结果、缓存或错误响应泄露。
- KB 文件写入、权限记录、元数据和向量索引失败时不会留下伪成功状态。
- 实验性数据源代码保留，但默认不可从 API 调用。

## 2. 非目标

- 不实现 NAS、SMB、WebDAV 或钉钉连接器。
- 不实现组织架构、部门继承、岗位权限或离职交接。
- 不为通用数据库/API 数据源新增生产级 SSRF 与凭据保险库。
- 不重写整个 `rag/api.py`，只提取本阶段需要复用的安全边界。
- 不提供“覆盖同名文件”功能；同名上传在本阶段明确返回 `409 Conflict`。

## 3. 根因

现有问题不是单个条件判断遗漏，而是安全决策分散：

- 部分端点调用 `verify_api_key`，部分手工解析 Bearer token，部分完全不认证。
- KB scope、共享记录和文档权限在不同接口中分别判断，语义不一致。
- 最终回答缓存发生在权限过滤之前，缓存键只有问题文本。
- 文件既通过鉴权下载接口提供，又被 `/data/upload` 静态挂载直接暴露。
- 文件、SQLite 元数据和 Qdrant 向量没有统一的提交/补偿顺序。
- 实验性数据源接口已经对外注册，但没有产品入口、租户边界或安全约束。

因此本阶段采用“安全边界收敛”，而不是继续在每个端点添加独立判断。

## 4. 认证与授权边界

### 4.1 认证

- `Settings.auth_enabled` 默认改为 `True`。
- 只有显式设置 `RAG_AUTH_ENABLED=false` 才进入本地开发匿名模式。
- 启动时若匿名模式开启，记录高优先级安全警告。
- `/register` 和 `/login` 保持公开；其他业务 API 默认要求有效 JWT 或配置的 API key。
- Bearer token 解析统一使用严格格式，不再使用无条件 `replace("Bearer ", "")`。

### 4.2 统一 principal

新增一个小型 API 安全模块，集中提供：

- `require_user(...) -> dict`：返回完整用户记录，失败为 `401`。
- `require_admin(...) -> dict`：在 `require_user` 基础上校验管理员，失败为 `403`。
- `require_kb_view(kb_id, user)`：调用现有 `check_kb_permission(..., "view")`。
- `require_kb_edit(kb_id, user)`：调用现有 `check_kb_permission(..., "edit")`。
- `require_doc_view(doc_name, kb_id, user)` 和 `require_doc_edit(...)`：调用现有文档权限工具。

端点不得把客户端提交的用户 ID、用户名或 scope 当作授权依据。

### 4.3 KB 规则

- `private`：所有者和管理员可查看；明确授予的共享编辑者仅在共享记录仍存在时可编辑。
- `shared`：所有者、管理员和 `kb_shares` 中的用户可查看；只有 `permission="edit"` 的共享用户可修改。
- `public`：所有已登录用户可查看；只有所有者、管理员或共享编辑者可修改。
- 元数据缺失的 Qdrant collection 视为不完整资源。普通删除接口返回 `409`，不得跳过 owner 检查。
- 列表、详情、查询、目录生成、概述生成、改名、删除均使用相同规则。

### 4.4 文档规则

- KB 可见不等于其中所有文档可见。
- 检索结果在生成回答之前必须按文档 ACL 过滤。
- `ShareRequest.permission` 必须真实写入 `document_shares.permission`。
- 受保护文件不允许被覆盖、删除或改变可见性。
- 无权限记录的历史文件只允许管理员访问；不再默认视为公开。迁移时由管理员显式认领或标记为公共。

## 5. 文件与索引生命周期

### 5.1 默认文件库上传

流程固定为：

1. 在读取完整请求体前验证用户。
2. 清理文件名并校验扩展名、大小。
3. 若同一 KB 已有同名权限记录或物理文件，返回 `409`。
4. 写入同目录的随机临时文件。
5. 完成解析、分块和嵌入。
6. 创建权限记录并写入 Qdrant。
7. 原子重命名临时文件为最终文件。
8. 任一步失败时删除临时文件、已创建的权限记录和本次写入的向量。

本阶段禁止覆盖，以避免旧向量和新文件混合。

### 5.2 KB 专属文件

- 文件持久化到 `data/kb_files/{kb_id}/{document_id}/{safe_filename}`。
- `kb_documents.file_path` 保存实际持久路径，不再指向不存在的 `data/upload/{filename}`。
- TOC 和概述生成从该实际路径读取。
- 删除顺序为：标记删除中、删除向量、删除元数据与权限记录、删除物理文件。失败时记录错误并保留可重试状态。

### 5.3 下载与前端复制

- 删除 `/data/upload` 静态挂载。
- 所有原文件下载只走 `/files/{filename}/download`。
- 前端“添加到知识库”通过带 JWT 的下载接口取得 Blob，再上传到 KB；未授权下载直接终止。
- `/data/charts` 可继续静态挂载，但不得包含用户上传原文件或数据库。

## 6. 检索与缓存

本阶段禁用最终回答缓存。原因是安全缓存键不仅需要用户和 KB，还必须在权限撤销、文档删除、scope 变化后立即失效；当前系统没有可靠的 ACL 版本。

- `RAGPipeline._prepare_context` 不在权限过滤前读取回答缓存。
- `query` 和 `query_stream` 不写入最终回答缓存。
- RedisCache 类保留，供未来实现带 `principal + kb_id + ACL version + filters` 的安全缓存。
- 文档检索、rerank 后必须过滤 ACL，再构造 prompt 和 sources。
- 流式与非流式路径使用同一权限过滤流程。
- 知识库详情页发起的流式查询必须显式携带当前 `kb_id`；服务端先校验该 KB 的查看权限，再创建或选择绑定该 KB 的 pipeline。不得静默回退到默认 `rag_docs`。

这一选择牺牲少量重复问题性能，换取权限撤销立即生效和确定的数据隔离。

## 7. 数据源封存

- 新增 `Settings.data_sources_enabled: bool = False`。
- 当功能关闭时，所有 `/sources` 端点返回 `404`，不暴露实验功能。
- 当功能显式开启时，端点仍要求管理员身份。
- 列表响应不得返回完整 Authorization headers、密码或连接字符串。
- 当前 `RSSSource`、`APISource`、`DBSource` 和数据库表保留，不删除数据。
- 在完成 URL/IP allowlist、DNS 重解析防护、只读凭据管理和专用 NAS connector 设计前，生产环境不得开启该开关。

## 8. 错误处理与审计

- `401`：未登录、token 无效或过期。
- `403`：身份有效但无资源权限。
- `404`：资源不存在，或实验性数据源功能关闭。
- `409`：同名文件、元数据缺失、资源状态冲突。
- `413`：文件超过大小限制。
- 对外错误不返回本地路径、连接字符串、数据库异常全文或密钥。
- 安全拒绝日志记录 user ID、动作、资源 ID 和结果，不记录 token、密码或文件正文。

## 9. 测试策略

所有修复按 TDD 实施，每个问题先写能够在旧代码上失败的测试：

- 匿名上传真实文件必须返回 `401`，且磁盘与向量库不变化。
- 未认证访问一个真实存在的 `/data/upload/{name}` 必须无法得到内容。
- 用户 A 的私有回答不能被用户 B 通过相同问题命中。
- 非共享用户不能列表、查看或查询 `shared` KB；被共享用户可以。
- public KB 中的 private 文档不会出现在检索结果或 sources。
- 文档 `view` 和 `edit` 分享产生不同权限结果。
- metadata 缺失的 KB 不能被普通用户删除。
- KB 上传后文件在临时文件删除后仍存在于记录路径，TOC/概述可读取。
- 数据源默认返回 `404`；启用后普通用户返回 `403`，管理员可进入受控路径。
- 认证默认开启；显式开发模式关闭时保留已有匿名开发行为并产生警告。

每个安全测试使用临时 SQLite、临时文件目录和隔离的 Qdrant 路径，不得读写生产 `data/users.db` 或共享模块级状态。

## 10. 实施顺序

1. 建立隔离测试夹具和统一认证 dependency。
2. 默认启用认证并封存数据源。
3. 修复匿名上传、静态文件泄露和前端复制路径。
4. 统一 KB/document ACL，并修复共享 edit 权限。
5. 禁用不安全回答缓存。
6. 修复 KB 文件持久化和删除补偿。
7. 让知识库详情页的流式查询显式绑定并校验当前 `kb_id`。
8. 执行后端全套测试、前端单测与构建、静态检查和独立代码审阅。

任何一步发现现有业务依赖被安全规则阻断，先补充明确的授权规则和测试，不恢复隐式放行。
