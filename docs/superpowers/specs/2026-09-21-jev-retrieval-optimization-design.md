# Jev 检索链路优化设计

## 1. 目标

本阶段使用 TypeSafe Jev 优化现有检索链路的速度、可扩展性和结构化决策能力，为后续规则增长和后台自进化提供统一的在线快速判断层。

当前普通 RAG 链路在生成答案前依次调用 DeepSeek 意图路由、DeepSeek 查询改写和外部 reranker，存在多次串行外部调用。新链路以两次结构化 Jev 请求替换路由与重排，并把查询改写改为有界降级路径。

成功标准不是单纯降低延迟，而是在权限和安全边界不变、准确率无明显退化的前提下降低生成前准备耗时和外部调用成本。

## 2. 范围

本阶段包括：

- Jev 服务端适配器、超时、重试、熔断和本机密钥配置。
- 第一次 Jev 批量判断：意图、复杂度、是否需要查询改写。
- 第二次 Jev 批量判断：候选块相关性、答案证据、前提冲突和提示注入。
- 条件式查询改写及最多一次检索重试。
- 与现有可靠性模型、执行轨迹和权限过滤的集成。
- 旧路由与旧 reranker 的降级后备。
- 影子运行、A/B 基准、知识库级灰度和性能报告。

本阶段不包含后台自进化实现，也不允许 Jev 执行权限判断、精确计算或自由生成工作流。后台自进化未来通过相同的版本化 Jev 协议生成候选问题集和策略。

## 3. 现有链路

当前主要路径为：

`安全检查 → 表格协调器尝试 → DeepSeek 路由 → DeepSeek 查询改写 → 向量与 BM25 检索 → ACL 过滤 → 外部 rerank → 文档注入过滤 → 可靠性门 → 生成答案`

主要问题：

- 路由、改写和重排是串行外部调用。
- 普通、清晰问题也无条件调用查询改写。
- 路由只返回 `rag` 或 `agent`，无法复用概率和不确定性。
- reranker 只提供单一相关度，冲突、证据充分性和提示注入由后续分散处理。
- 规则和链路继续增加时，串行判断会进一步拉长延迟。

## 4. 新链路

新链路分为在线预判、检索和候选判断三段：

```text
输入安全检查与权限上下文
  → Jev 预判（一次请求，三个并行问题）
  → 代码路由
  → 混合检索与 ACL 过滤
  → Jev 候选判断（一次请求，对候选块并行提问）
  → 固定代码策略筛选、排序和冲突处理
  → 可靠性门
  → 生成或固定拒答
```

普通 RAG 直接使用原问题检索，不再无条件调用 DeepSeek 改写。只有预判认为需要改写、首轮无足够候选或候选判断认为全部缺少答案证据时，才允许进行一次 DeepSeek 改写并重试检索。重试后仍无证据则可靠拒答。

## 5. 第一次 Jev 请求：预判

预判请求共享权限安全的最小状态，包括用户问题、知识库能力摘要、是否存在结构化数据、允许使用的工具类型及必要会话上下文。它不接收未授权文档内容。

一次请求中提交三个独立问题：

- `intent`（Choice）：`structured_query`、`retrieval_qa`、`tool_task`、`clarification`。
- `complexity`（Score 或 Choice）：`simple`、`multi_step`、`specialist`。
- `needs_query_rewrite`（Noul）：原问题是否不适合直接用于检索。

代码拥有路由控制权：

- `structured_query` 进入现有表格结构化查询协调器。
- `retrieval_qa` 进入混合检索。
- `tool_task` 进入受控工具流程；企业模式继续遵守现有 typed-evidence 限制。
- `clarification` 返回澄清请求。

Choice/Score 的置信度和完整概率分布进入执行轨迹。低置信度不得被当作确定动作；根据风险采用默认 RAG、澄清或旧路由降级。阈值必须通过本项目数据校准，不直接照搬文档示例。

## 6. 第二次 Jev 请求：候选块判断

混合检索和 ACL 过滤完成后，第二次 Jev 请求接收原问题、实际检索查询及权限可见的候选块。任何不可见文本不得发送给 TypeSafe。

每个候选块并行判断：

- `is_relevant`：是否与问题相关。
- `contains_answer_evidence`：是否包含支持回答的具体证据。
- `contradicts_query_premise`：是否反驳问题中的前提。
- `contains_prompt_injection`：是否包含试图影响模型行为的隐藏指令。

固定策略为：

- 注入块直接排除并记录。
- 包含答案证据的块优先。
- 相关但证据不足的块只能作为背景。
- 矛盾块保留在独立冲突集合中，回答必须明确报告冲突。
- 全部证据不足时最多触发一次查询改写重试。

Jev 的概率作为独立语义分数保存。现有 `score_source` 增加 `jev`，不得把 Jev 概率伪装成旧 reranker 分数。可靠性门只读取明确标注来源且已校准的分数。

## 7. 适配器与版本协议

新增独立 Jev 适配层，不让 pipeline 直接依赖 SDK 数据结构。内部协议包括：

- `state`：问题、能力、权限过滤后的候选和业务事实。
- `questions`：稳定 ID、问题集版本、原语类型、指令和判定标准。
- `answers`：选择或分数、概率、置信度、模型版本和耗时。
- `policy`：阈值、组合规则、降级策略和允许动作。
- `trace`：问题集版本、采用的判断、路由依据和最终效果。

API Key 仅从服务端环境读取，不进入代码、日志、轨迹、测试快照或 Git。SDK 客户端复用连接并设置严格超时。

## 8. 故障与降级

Jev 超时、限流、鉴权失败、响应无效或熔断开启时：

- 预判阶段降级到现有路由逻辑。
- 候选判断阶段降级到现有 reranker。
- 降级事件和耗时进入轨迹，但不向用户暴露密钥或内部错误。
- Jev 故障不得扩大权限范围，也不得绕过 ACL。

候选判断失败时，旧 reranker 的 `score_source` 仍为原有来源；两类分数不混用。降级链路需要独立测试，避免“新服务异常导致整个问答失败”。

## 9. 影子运行与灰度

迁移分四步：

1. Jev 影子运行：记录判断，不改变现有路由和排序。
2. A/B 评测：比较同一问题集的延迟、准确率、调用数和成本。
3. 指定知识库灰度：管理员选择知识库启用 Jev 主路径。
4. 全量启用：验收通过后将 Jev 设为主路径，旧链路继续作为熔断后备。

问题集版本、策略版本和灰度范围可独立回退。禁用 Jev 后无需重建索引即可恢复旧链路。

## 10. 性能与准确率基准

A/B 基准集包括：

- 意图集：普通问答、表格精确查询、计算、工具任务和含糊问题。
- 检索集：具有管理员确认答案和来源块的问题。
- 困难集：同义表达、跨块证据、冲突资料、提示注入和无答案问题。
- 真实集：从现有执行记录中脱敏抽样并由管理员确认标签。

每次运行记录意图耗时、改写耗时及触发比例、检索耗时、候选判断耗时、生成前准备耗时、首字时间、总耗时、外部调用次数、Token 和费用。性能报告给出预热与冷启动结果、样本数、P50 和 P95，不能只使用单次结果。

准确率指标包括路由准确率、Top-1/Top-5 证据命中率、引用正确率、错误拒答率和注入拦截率。

首期验收线：

- 生成前准备阶段 P50 至少降低 30%。
- P95 至少降低 20%。
- 普通问题的 DeepSeek 改写调用减少 70% 以上。
- 路由准确率不低于 95%。
- Top-5 证据命中率相对旧链路下降不超过 2 个百分点。
- 权限与提示注入测试全部通过。
- Jev 故障时旧链路降级测试全部通过。

## 11. 测试策略

- 适配器契约测试：SDK 响应映射、概率、置信度、版本和异常。
- 路由单元测试：所有意图、低置信度、无匹配和降级。
- 候选策略测试：证据、背景、冲突、注入和全无证据。
- Pipeline 集成测试：结构化查询、普通 RAG、条件改写和一次重试。
- 安全测试：ACL 前置、不可见文本不出边界、密钥不入日志。
- 韧性测试：超时、429、5xx、无效响应、熔断和旧链路恢复。
- 基准测试：固定语料与固定问题集上的 A/B 延迟和质量报告。

## 12. 隔离开发与合并

实现使用分支 `feature/jev-retrieval-optimization` 和工作区 `.worktrees/jev-retrieval-optimization`。现有 `main` 与 1002 服务保持运行；Jev 测试服务使用 1102 端口。

开发完成后先在隔离工作区运行专项测试、完整相关回归和 A/B 基准。只有达到验收线并经人工查看报告，才合并回 `main`。合并前可直接移除工作区回退，不影响在线应用。

## 13. 与自进化的衔接

后台自进化未来只生成版本化 Jev 问题集、策略和阈值候选，不直接修改在线稳定配置。候选使用本设计的回放基准和轨迹评测，在人工确认、知识库级灰度和可回退快照约束下晋升。
