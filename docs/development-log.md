# 开发日志（RAGv3 自演化系统）

> 这份日志按「**问题 → 证据（测量）→ 决策 → 结果（数字）→ 反思**」记录开发过程。
> 所有数字都来自仓库里的实测脚本，可复现；失败与返工也如实记录 —— 那部分往往比顺利的部分更值得讲。

## 0. 这套系统是什么（30 秒版）

一个**辅助式自我演化**的知识库问答系统：线上失败被记成"观测"，同类失败聚成"聚类"，由模型给出根因诊断，
经**五层门禁**（作用域 → 基准 → 影子 → 灰度 → 回滚）后产出三类制品 —— 提示词/查询改写候选、
**代码补丁**候选、**知识缺口工单**。**系统永不自动合入**：每一次变更都由管理员点击，
每条补丁都能一条命令回滚。

技术栈：Python / FastAPI / SQLite / Qdrant / Vue 3 + TypeScript / pytest / vite / ruff，
以及"用 `difflib` 合成 diff""用 `ast` 建符号索引"这类确定性工具的深度使用。

## 1. 2026-10-09：先让诊断可信，再谈自动化

**问题**：诊断（哪个环节坏了）是整条链的输入。此前靠启发式，中文诊断在英文代码路径上命中率为 0，
排序退化成文件字母序。

**证据与决策**：
* 管理员标签从 4 条扩到 **7 条**（每条附全库探针证据）；其中一条是**负向标签**——"内容在、金额被脱敏 ⇒
  价格答不出来是**正确行为**"，并**刻意不写型号串**，否则确定性包含检查会把这条脱敏确认误推成"取用侧缺陷"。
* 新增 `diagnosis-v10` **无证据护栏**：没有管理员标签却断言"库里没有"时，`root_cause` 必须写明"需管理员标签"
  （硬校验）——因为那个结论正是后续"知识缺口工单"的输入，不能让一次猜测变成一张工单。

**结果**：无标签 40 行开发集 **33/39 = 84.6%**，稳定行 35/39，契约违规 4/78（与旧版持平）；
此前 v8 的 31/39 **未复现** ⇒ 判定那次下降是噪声而非回归。

**反思**：一开始我把 v8 的下降当成回归；测量两次才敢说"是噪声"。**先定判据、再下结论**是这套系统能往前走的原因。

## 2. 2026-10-09：从"猜文件"到"点名文件"

**问题**：补丁生成器按"诊断措辞出现次数"排序文件。中文诊断贡献中文二字组，命中率为 0 ⇒ 退化为字母序；
证据边界的缺陷因此产出了三份改 `rag/agent.py` 的补丁。

**决策**：新增 `rag/evolution/symbols.py` —— 用 `ast` 建符号索引（143 文件 → 1696 符号，约 1.5 秒），
`_rrf_fuse` 直接解析为 `rag/retriever.py:230-266`；再用**靶心窗口**（目标行 ±120 行）代替"只给前 400 行"
——后者在目标位于第 745 行时什么也看不到。

**结果**（无模型调用的确定性验收）：无定位时首目标是"猜的" `rag/bm25_store.py`，有定位时是
**帧点名的 `rag/pipeline.py`**；窗口 `580–820` 覆盖第 745 行；中文诊断里的 `_finalize_rag_context`
与 `_rrf_fuse` 被解析为 `rag/pipeline.py` 与 `rag/retriever.py`。

## 3. 2026-10-09：彩排抓出"单元测试全绿但机制从不触发"

**问题**：worker 在生产里空转（`scanned=0`），"回路端到端可用"只有各部件用例，没有一条从观测走到制品的实证。

**做法**：在**数据库副本**上（SQLite backup API 取一致副本）注入三族失败并跑完整回路。

**结果与最关键的发现**：工单**一张都没产出** ✗。根因是**我自己的准入判据写错了**：它按聚类的
`root_cause_feature == "undetermined"` 判准入，而那是**聚类器**写的字段；"内容缺口"其实是**诊断草稿**的结论。
**我的单元测试之所以全绿，是因为夹具按我的错误假设塞了那个字段** —— 典型的"测试固化了错误假设"。
改为以最新草稿为准后重跑：**产出 4 张工单** + 3 份候选，三条不变量全部成立。

**反思**：端到端彩排的价值不是"再跑一遍"，而是它能证伪**你以为**成立的假设。这是我最愿意讲的一段经历。

## 4. 2026-10-10：把补丁生成成功率从 58% 提到 100%

**问题**：残余失败是"模型输出质量"，约每 4 次生成就有 1–3 次被边界拒绝。

**测量先行**：先建**测量台**（`scripts/measure_patch_generation.py`），复用 worker 同一套准入，
只读、不需要语料，输出成功率、失败类别、真实调用数（含重试）。
基线 **7/12 = 58.3%**（首试 41.7%）⇒ 距 80% 判据有差距，但**先有了可比基线**。

**基线顺带暴露一个自伤式缺陷**：5 个失败里有 2 个是 `timeout`，而生成器超时是**默认 90s、worker 从没传**
⇒ 等于**在截断一个慢但可能成功的调用**。修掉（默认 600s）后复测：不再有 timeout，但仍是 0/2 通过
⇒ 说明剩下的问题**不在超时**。

**关键判断**：两类上下文规模（400 行 / 1600 行）下，失败都以 `does_not_apply` / `corrupt_patch` /
"压根没给 diff"为主 ⇒ **上下文不是约束**；症结是**模型在手写 `@@ -a,b +c,d @@` 并核对行数算术**。

**决策**：加 `edits` 输出格式 —— 模型只给「路径 + 精确 `old_text` + `new_text`」，
**diff 由我们用 `difflib` 合成** ⇒ hunk 头与上下文**构造上自洽**，`corrupt_patch` 与 `does_not_apply`
在这条路径上不可能发生；边界一个字没改（路径白名单、黑名单、配额、`git apply --check` 照跑）
⇒ 是**双重保证**而不是放宽。

**结果**（严格同样本 6 对 × 2 次、串行）：`diff` **8/12 = 66.7%** vs `edits` **12/12 = 100%**（首试 100%、零重试），
单次耗时均值 110s → 59s。默认因此切到 `edits`，回退只需一个环境变量。

**反思**：我一开始做"加大上下文"的对照时**换了样本**（top-up 选了另一批），数字不可比 —— 这促成了
`--observation-ids`（固定样本）与帮助文本里那句"做 A/B 必须用它"。**测量本身也要防自欺。**

## 5. 2026-10-11：应用这一步的安全与"堆放治理"

**问题一（安全）**：批准之后的手工流程没有安全网 —— 没人检查补丁是否还能套用、改完还能不能导入、
服务起不来怎么办。

**决策**：`POST /code-candidates/{id}/apply`，三道前置检查（**能否应用** → **`import rag.api` 冒烟** →
**补丁自带的目标测试**），任一失败就**回滚并且不重启**；全过才写重启请求，由**分离式助手**执行：
等端口释放 → 拉起服务 → 轮询 `/health` → **起不来就回滚补丁再拉一次**（坏部署的结果是"旧代码在跑"，
而不是"什么都没在跑"）。应用前还会跑**全量套件** —— 因为补丁自带的 `test_paths` 是**模型自己挑的**，
拦不住"改坏别处"，那正是屎山的主要来源。

**问题二（用真实补丁暴露的两个 bug）**：
* 面板给出的应用命令带 `--3way`，而导出的补丁**没有 `index` 行** ⇒ 三路合并必然失败
  （`repository lacks the necessary blob`）—— 照抄就会踩 ✗；
* 同一份补丁"从文件能应用、从 stdin 失败"：`read_text` 把 CRLF 归一成 LF，而仓库文件仍是 CRLF ✗。
修法：命令与状态判断统一为**不带 `--3way`**，并且一律**写临时文件再 `git apply <file>`**（与运维命令同机制）。

**问题三（屎山风险，用户提出）**：查数据发现 **19 条代码补丁挤在 3 个文件**（`rag/reranker.py` 11 条、
`rag/agent.py` 7 条），其中 **5 条是同一个"同义对齐"想法的不同写法** ✗。根因是准入**按观测**去重，
而某个聚类有 **112 个成员** ⇒ 理论上一口气能产出 112 条。

**决策**：加**聚类级未决闸**（一个聚类只要还有一条未决候选，就不再为它的任何成员生成），
并且**轮内也挡**（轮初快照挡不住同一轮里的其他成员 —— 这一点是我写测试时才发现的，我的第一版修复有这个洞）。

**结果**：worker 套件 67 passed；两个聚类各得一条、再跑一轮零新增；驳回只释放**聚类级**闸，
不会让**同一个观测**自动重试（那条规则是有意为之）。

## 6. 2026-10-11（续）：把"手动重启"变成"一键重启"，并补上第三道闸

**问题一**：批准之后的手工流程没有安全网（补丁是否还能套用、改完还能不能导入、服务起不来怎么办）。
**决策**：`POST /code-candidates/{id}/apply` —— 三道前置检查（能否应用 → `import rag.api` 冒烟 →
补丁自带的目标测试）+ **应用前跑全量套件**（补丁自带的 `test_paths` 是**模型自己挑的**，拦不住"改坏别处"），
任一失败就**回滚且不重启**；全过才由**分离式助手**执行重启：停掉当前服务 → 拉起 → 轮询 `/health` →
**起不来就回滚补丁再拉一次**（坏部署的结果是"旧代码在跑"，而不是"什么都没在跑"）。

**问题二（我自己的 bug，被"手工做一次"抓出来）**：助手**从不停止当前服务** ✗ —— 它只等端口释放，
而按钮流程里没人释放端口 ⇒ 60 秒后它只会记一句"端口一直没释放"就退出 ✗✗，也就是**这个功能本来就是
不完整的**。是我**按你说的手动重启了一次**才发现的 ✓。修法：接口把自己的 pid 交给助手，助手先等几秒
（让 HTTP 响应先回到浏览器）再终止它，并在回滚路径里先结束**自己刚拉起的那个进程**（否则端口被它占着）。
另外补了一条用例：**助手源码是字符串，语法错只会在运行时炸 ⇒ 显式编译一次**。

**问题三（用户提出的"会不会变屎山"）**：查数据 —— **19 条代码补丁挤在 3 个文件**，
`rag/reranker.py` 11 条，其中 **5 条是同一个"同义对齐"想法的不同写法** ✗。
根因是准入**按观测**去重，而某个聚类有 **112 个成员** ⇒ 理论上一口气能产 112 条。
**决策**：① **聚类级未决闸**（一个聚类还有未决候选就不再生成，**轮内也挡** —— 这一点是我写测试时才发现
我第一版修复有这个洞）；② **应用前全量测试**；③ **近重复提示**（用 `ast` 符号索引把改动落到**具体函数**上，
键形如 `rag/reranker.py:Reranker.rerank`，两个以上同键就提示"这是同一条改动的变体，建议只留一条"）。
三道都是**提示/门禁**，从不自动改动代码 ✓。

**结果**：后端 **2015 passed** ✓、前端 **211 passed**（32 文件）+ 类型检查 + 构建 ✓；
「应用并重启」端点实测已在线（无令牌返回 401 = 路由存在 ✓）。

**另一份输入的核验**：另一 agent 提交了一份系统审计与升级路线图（`docs/rag-system-audit-and-upgrade-roadmap.md`）。
我逐条对照自己的测量：**多数与我的实测一致**（真实供给为 0、单文件补丁上限、20 例基准分辨率不足、
本地库锁瓶颈）。其中一条 P0 我**验证为真**并采纳：**用户点踩/投诉没有进进化池** ——
`POST /feedback` 只写 users 库的 `add_feedback`，**完全不碰进化队列** ✗。而点踩是**带人工标注**的最高信号失败源，
正是"供给为 0"最该修的地方。列为下一项。

## 7. 2026-10-11（再续）：把用户点踩接进回路（外部审计的 P0，我核验后采纳）

**来源**：另一 agent 提交的系统审计把"用户负向反馈未进进化池"列为 P0。**我去核验**了它 ——
`POST /feedback` 的实现只调用 `user_db.add_feedback(...)` 写用户库，**完全不碰进化队列** ⇒ **属实** ✓。

**为什么这条最值得先修**：整套回路的瓶颈是"真实失败供给为 0"（worker 诚实地空转 `scanned=0`），
而**点踩是带人工标注的最高信号失败源** —— 用户已经替你说了"这个回答不对"，还知道是哪一条消息。
修它同时解决**供给**与**标签**两件事。

**设计（每条都有理由）**：
* 走与 pipeline **同一个** `FailureRecorder`（非阻塞入队）⇒ 存储、跳过规则、阻断语义与线上一致，
  不另造旁路；
* `route="feedback"`：这是**用户报告**的失败，不是路由判定出来的 ⇒ 来源如实区分，聚类也能把
  "用户不满意"与"检索没召回"分开看；
* **只存结构化信号**（该消息的可答性/置信度/kb/有无留言），**留言文字绝不入库** ⇒ 那是用户内容，
  落在红线之外；
* 同一条消息**重复点踩不重复入库**（同一失败记两次是噪声，不是信号）；
* 整段 try/except ⇒ **记录失败绝不影响反馈本身**（用户点了踩就该成功返回）。

**结果**：3 条用例（点踩→观测且不含留言文字、空问题跳过、记录器抛错时反馈仍成功）✓。

**反思**：这一条不是我"想出来"的，而是**别人的审计 + 我去核验**得来的。两份输入的价值不同：
自己的测量能证伪自己的假设，外部审计能指出你根本没看的地方 —— 前提是**逐条核验**，
而不是照单全收，也不是不予理会（同一份审计里我采纳了这条，也明确不采纳多模态与服务型数据库那两条，
理由都写在给用户的回复里）。

## 8. 2026-10-11（三续）：端到端验收、同一失败模式的第二次，以及两条审计条目的核验

### 8.1 端到端验收（真登录 → 真提问 → 真点踩 → 真观测）

在**运行中的服务**上：登录 → 建会话 → 提问（一个语料里确实没有的问题）→ 系统诚实回答"资料不足" →
对该条回答**点踩** → 查询进化库：

```
obs#160 route=feedback 可答性=insufficient_evidence feedback=negative_with_comment kb=unknown
```

✓ 点踩落成观测、带结构化证据、**不含留言文字**（红线 ✓）。观测总数 158 → 160。

### 8.2 同一个失败模式的**第二次**：单测绿、接线没接

写完助手后我跑用例，**3 条全绿** —— 但线上点踩毫无效果。原因：我用 `replace` 插入处理器里的那**一行调用时没加断言**，
替换**静默失败**了 ⇒ 助手成了**死代码**，而用例**直接调用助手** ⇒ 当然全绿 ✓✗。

这与第 3 节（彩排抓出"单元测试固化了错误假设"）是**同一类失败**：**测了部件、没测接线**。
本次的修法：① 插入时**断言**替换真的发生 ✓；② 补一条**端点级**用例 —— 走 `POST /feedback`、断言观测助手**真的被调用**
（正向反馈则不调用）✓✓；③ 失败也要留痕：把观测记录失败写进 `artifacts/feedback-observation.log` ✓
（正是这份日志帮我在"静默失败"里定位到 `user_id` 漏传那一步 ✓）。

顺带修的两个小问题：漏传 `user_id`（`TypeError` 被 except 吞掉 ⇒ 观测根本不落库 ✓）；
`ExecutionTrace.decision_metadata` 有**键白名单**，我在元数据里放的溯源键被静默丢弃 ⇒ **去重形同虚设**，
已把 `feedback_message_id` 加入白名单 ✓。

还有一条**操作教训**：我的手工重启是 racy 的 —— `kill → 等 4 秒 → start`，若端口未释放则 `start.py` **拒绝启动**，
而**旧进程继续服务** ⇒ 健康检查通过、请求却打到旧代码上（实测：13:38:08 的点踩打到旧进程，13:38:29 新进程才起来）。
正确的判定是**比较进程启动时间与源文件修改时间** ✓（正是我写的重启助手做的事：等端口真正释放 ✓，
粗糙的是我手工那几步）。**这条也说明"手工流程不可靠"，正是做一键重启的理由。**

### 8.4 「看起来对了、其实什么都没做」的三种形态（同一功能里连着踩了三次）

点踩这条功能，我连着遇到**三种不同的静默失效**。它们的共同点是：**单测全绿、接口照常 200、日志干净**，
而实际上什么都没发生。值得单独记下来，因为这类 bug 比崩溃难查得多：

| # | 形态 | 为什么看不见 | 怎么暴露的 |
| --- | --- | --- | --- |
| 1 | **接线漏了**：处理器里那一行调用没插进去（`replace` 静默 no-op），助手成了死代码 | 用例**直接调用助手** ⇒ 全绿；接口返回 200 与以前一模一样 | **在运行中的服务上真的点一次踩**，再查库 |
| 2 | **参数漏传**：`get_message_reliability(message_id)` 少一个 `user_id` ⇒ `TypeError` | 被宽泛的 `except` 吞掉（当时的日志只在服务进程里、而服务是分离启动的 ⇒ 看不到） | 在进程内**逐步复现**那条路径，让真实异常打出来；并补上可查的失败日志 |
| 3 | **键名读错**：去重读 `decision_metadata`，而存储返回的是 `details_decision_metadata` ⇒ 永远 None | 去重"看起来"在跑，只是从不命中 | 打印**真实行**的键名，用真实键名补一条行为用例 |

**教训（写给未来的自己）**：
1. **部件测试不等于接线测试**：对"必须发生"的调用，要有一条**走端点**的断言（本次补了两条）；
2. **宽泛的 `except` 必须有可查的留痕**，否则它会把"功能没生效"变成"什么都没发生"；
3. **凡是读存储的代码，键名要按真实行的键名写**，并用真实形态的夹具钉住（真实键名、真实前缀）；
4. **最后一步永远是"在真实环境里跑一遍并核对数据"** —— 本次三处都是这样才暴露的。

**顺带**：这次也确认了"手工重启不可靠"（racy：旧进程还在服务时，健康检查会骗过你），
而**判断标准是"进程启动时间是否晚于源文件修改时间"** —— 这条已用于验证服务是否真的带上了修复。

#### 关于切块：我连错三次，最后**撤回结论**

审计说"表格与行被截断"。我先给了"属实"的结论，随后自己把它推翻了三次：

| 我的假设 | 怎么被推翻的 |

## 9. 2026-10-11（四续）：多轮改写（默认关闭的开关）与一条"我修错了模块"的教训

### 9.1 多轮上下文改写：缺口确认，按"默认关闭"补上

核验结论**属实**：`rewrite_query(question: str) -> str` **只吃当轮问题**，所以"它呢？/那这个多少钱？"
这类指代会被**无上下文改写**。而**回答生成**那条路本来就有上下文（`self.memory.build_messages(sid, …)`）——
缺口只在**检索前的改写**这一处。

做法（复用已有，不造新接口）：`DialogueMemory` 里**本来就有** `get_recent_messages(session_id, n)`
与 `get_summary(session_id)`；`rewrite_query` 增加可选的 `history` / `summary`；
pipeline 里加一个**统一入口** `_rewrite_for_retrieval(question, session_id)`，由新配置
`query_rewrite_history_turns`（**默认 0 = 关闭**）决定是否带上最近几轮。

**为什么默认关闭**：本轮**没有**多轮评测集，开启后的检索质量提升**未被测量** ⇒
按本项目的纪律，不能把未测量的改动设为默认。0 轮时调用方式与既有代码**逐字节一致**（用例钉住），
要开启只需改一个配置，但**开启前应先建一个小型多轮评测集**再谈提升。

**（这一节也如实记了我自己的两个错）**：插入函数时把 `@retry` 装饰器与 `rewrite_query` 隔开了
（装饰器挂到了新函数上），以及把会话变量名臆想成 `sid`（真实名字是 `session_id`）——
两处都是 **lint 当场抓住**的。这再次印证：**工具链的价值在于把"我以为"变成"实际如此"**。

### 9.2 "我修错了模块"：一次值得记住的误诊

审计说"切块结构损坏"，我发布过"属实"的结论，随后自己**连撤三次**（三次坏指标已记在 §8.3 上方）。

`corpus_missing` / `fixture_miss` / `database_unavailable` / `database_locked` / `database_schema` /
`unauthorized` / `credential_missing` / `upstream_rate_limited` / `upstream_timeout` / `network_error` /

1. **绝不出内容** —— 子进程输出可能引到语料文本，而报告、门禁轨迹、审计都要能安全展示；

## 12. 2026-10-11（七续）：跑沙箱这一步，暴露了同一类问题的四种形态

第 1 项任务（把队列里剩下的 #26、#27 跑沙箱）本身只花了两次运行，但**为了让"跑沙箱"这句话有意义**，
连着修了四处 —— 它们的共性都是：**一个与候选无关的原因，被记录成了关于候选的结论**。

### 12.1 未跟踪文件被当成"主树脏"

沙箱要求主树干净，用的是 `git status --porcelain`，而它**包含未跟踪文件**。仓库里躺着三份别的工具
写下的文档（未跟踪），于是**每一次**沙箱运行都判"主树脏"并拒绝 —— 一个与测量毫无关系的临时文件，
挡住了整条验证路径。而 worktree 是 `--detach HEAD` 建出来的，**未进任何提交的文件到不了那里**，
也就不可能影响被测的东西。修法：判定收窄到已跟踪文件（`--untracked-files=no`）；已跟踪的改动仍然拒绝，
因为那时"被测代码"与操作者以为看到的不一致。

### 12.2 环境问题被写成"驳回"，于是**吃掉了一条候选**

旧逻辑把所有"没应用成功"都写成 `rejected`。而它可能的原因是主树脏、git 问不动、worktree 建不出来、
超时 —— 一个**什么都没应用**的运行，把候选 #26 写成了 `rejected`，而 `rejected` 是终态：
它再也无法被验证。这与沙箱自己文档里对回放写下的原则直接冲突（"跑不起来是错误，不是驳回：
环境缺失不是关于候选的证据"）。修法：报告带上 `environment` 标记，这类报告**不写任何状态**，
写回函数直接拒绝并说明"候选状态保持不变"；`does_not_apply`、边界违规、目标测试失败仍然驳回。

**两次人工修复**（走审计表，`action=advance`，备注写明缘由）：#26 从 `rejected` 退回 `candidate_testing`；
#26/#27 再退回一次，理由是下面的 12.4。

### 12.3 metrics 把"结论"当成"原始载荷"，于是有数字却显示没有数字

`run_patch_sandbox` 存进 `report.benchmark` 的**已经是** `patch_verdict` 比好的结论；
而 `sandbox_gate_metrics` 又把它当原始回放载荷送进 `patch_verdict` ⇒ 形状不对 ⇒ 永远判 None ⇒
metrics 写着 `verdict_unavailable`，**同一份报告的详情里却带着完整结论**（实测 #26/#27）。
审查台因此被告诉"没有数字"，而数字就在手边。修法：以 `passed` 键识别一份结论（`patch_verdict` 必写它），
其余仍显式标注"没有可比对照"。

### 12.4 无凭据的回放会产出一份**关于空无的结论**

沙箱刻意剥掉所有 `RAG_*`（即宿主 `.env` 的凭据）。但"没有凭据"并不等于"回放跑不起来"：
**检索仍在本地照跑**，只有生成全部失败并被兜底 ⇒ `failed_calls` 仍是 0、prep 也超过守卫线（1ms）
⇒ 证据守卫放行 ⇒ 两侧**一样坏**地比出 `route delta +0.0pp` ⇒ 一份"无回归"的结论被写进轨迹、显示成数字。
在无凭据的 worktree 里的实测：`prep_p50_ms = 6.7`、`failed_calls = 0`、`route 0.45`。
对照组（在仓库根、磁盘上有 `.env`）：`prep_p50_ms = 7010`、`route 0.5`。

修法：**受支持的运行器只在持有 fixture 时才请求回放**（fixture 回放的是录下的 seam，不需要凭据），
否则二层对照如实记为"未在此测量"。真正的二层对照属于管理员在宿主上做的 A/B —— 那一步有凭据。

### 12.5 于是 #26、#27 现在的沙箱条目是什么

```
sandbox passed: the patch applied and the target tests plus the fixed regression net are green;
the layer-2 regression A/B is not measured here (the sandbox carries no credentials)
and belongs to the administrator after applying
```

一句话：**"能应用 + 目标测试与固定回归网通过"**，而**不是**"没有回归" ✓。数字在宿主 A/B 里。

## 13. 2026-10-11（八续）：第 1-3 项收口

### 13.1 第 1 项：把 #26、#27 跑完沙箱与宿主对照

沙箱（如实条目）：两条都"**补丁可应用 + 目标测试与固定回归网通过**"，二层对照按设计记为
**未在此测量**（沙箱无凭据）。宿主 A/B 跑了**两轮**（串行、独占）：

| | 第一轮 | 第二轮 |
| --- | --- | --- |
| #26 | legacy 侧 route **-2.5pp** ⇒ failed | route **0.0pp** ⇒ passed |
| #27 | legacy 侧 route **-2.5pp** ⇒ failed | route **0.0pp** ⇒ passed |

**同一命令、同一快照，结论翻转** ⇒ 那 2.5pp 是**噪声**：40 个样本里恰好是 **1 个用例**的量级。
而这两个补丁一个改 `PromptManager.list_versions`、一个在 `create_agent_tools` 里兜 ValueError，
**都不碰路由** —— 它们不可能真的移动 legacy 路由 2.5pp。

这条把"基准分辨率不足"从一句判断变成了可复现的现象：**route 阈值是 0pp（从不放宽），而 20 例基准的
最小可分辨单位是 5pp/例（40 样本时 2.5pp）** ⇒ 一个用例的抖动就能把一次测量判成回归。
纪律不变（不放宽阈值），但**结论必须带上分辨率**：这两条的诚实说法是"在当前分辨率下测不出回归，
也测不出改善"，而不是"通过"或"回归"。

### 13.2 第 2 项：#20 的观察窗——**开着的，但零样本**

`#20` 17:30 上线并重启成功。查上线之后的证据：**新增观测 0 条**（全库最近一条观测在 13:56，
即上线之前）⇒ **没有任何流量经过** ⇒ 观察窗收不了口，`stable` 与"回滚"都没有依据。
这不是代码能补的：窗口要靠真实使用来填（当时定的触发是 200 次调用或 24 小时）。

**顺带发现一个真实缺口**：五层的"回滚"端点只处理**问题集灰度**（撤销注册、百分比置 0）；
对**代码补丁**，回滚 = 执行反向命令 + 重启（人工动作），**端点不做这件事**。
也就是说"一键应用"有了对应物，而"一键回滚"还没有 —— 这是第 2 项真正的待办。

### 13.3 第 3 项：宿主测量独占锁（并顺手挖出一个 Windows 平台坑）

并发争用会被记成候选的问题（实测：一侧 26 次调用失败，单独跑两次都是 0），所以 A/B 现在
用 `O_CREAT|O_EXCL` 的文件锁**拒绝启动第二次**，并报出持有者的 pid 与时长；pid 已消失或锁超过六小时
则**接管**并如实报告接管事实。四条用例 + 一次真实争用验证（手工持锁，看它拒绝且不碰服务商）。

**那个坑值得单独记**：存活检测原本用 `os.kill(pid, 0)`。在 **Windows** 上这不是"探测存在"，
而是调用 `TerminateProcess` —— **检查谁就杀谁**。表现是两次运行"零输出、退出码 1"：
pytest 与冒烟脚本各自在检查**自己的 pid** 时把自己杀掉了。修法是 Windows 走进程列表，
而 POSIX 才用 `os.kill(pid, 0)`；问不出来时一律"当作存活"，绝不靠猜测夺锁。

## 14. 2026-10-11（九续）：一键回滚建成，并在真实系统上走通 apply → rollback → re-apply

### 14.1 建成了什么

`POST /code-candidates/{id}/rollback`，与 apply **完全对称**：补丁必须当前确实已应用；反向之后必须
**还能导入**、**目标测试必须通过**；任一失败就**把补丁放回**、服务不动。重启助手现在知道自己在替哪种
动作善后（应用失败 ⇒ 反向；回滚失败 ⇒ **重新应用**）。**已提交的补丁会被拒绝**并指名那次提交
（`git apply -R` 会留下"某次提交的逆"，撤销提交的正道是 `git revert`）。

### 14.2 演练（真实系统，四步，每步全量套件 + 重启）

| 步骤 | 结果 | 工作树 |
| --- | --- | --- |
| 批准 #26 → 应用 | 套件 **2044 通过** → 重启 → 健康 | `prompt_manager.py` +22/-2 |
| 批准 #27 → 应用 | 套件通过 → 重启 → 健康 | 两文件 +29/-3 |
| **回滚 #26** | `reverted: true`、`rolled_back`、套件通过 → 重启 → 健康 | **只剩 `agent.py` +7/-1** |
| 审计修复 → 再应用 #26 | 套件通过 → 重启 → 健康 | 两文件 +29/-3 |

第三行是重点：**回滚把 #26 从运行中的代码里干净摘掉，而 #27 原地保留**；回滚之后套件仍然全绿、服务健康。
这条路径此前只有"手打一条命令"。

### 14.3 演练暴露的两个真实缺口

**缺口一：证据齐了，但没有"批准"这一步就应用不了。** 第一次演练在第 1 步就被拒：
`只有已批准的补丁才能应用（当前状态：awaiting_verification）`。`#26/#27` 已有沙箱条目与两轮宿主对照，
但状态仍是"待验证"⇒ **把"证据齐"变成"可应用"的动作就是管理员的批准**。这条本身是对的（红线：
系统永不自动应用），演练里补了两条批准决策（走接口、留审计）。

**缺口二：回滚之后无法通过接口重新应用。** 回滚把状态写成 `rolled_back`，而它是**终态**；
状态机里 `canary → approved_for_canary` 也不是合法转移 ⇒ **"回滚 → 再应用"在接口层面是断的**。
演练里用一次**审计式人工修复**绕过（备注写明缘由），但这是设计缺口，两种诚实修法：
① 回滚后从**同一个聚类重新生成候选**（聚类仍处于"已批准生成候选"，这是设计里本来就有的路）；
② 给回滚一个"撤销并回到可应用"的语义 —— 这需要状态机支持，属设计变更，应由人决定。

### 14.4 一条小的卫生问题

助手跑的那次全量套件里，**接口用例会往 `artifacts/service-control.log` 写行**（日志里那几行
`candidate 1: …` 就是测试写的）。它们与真实运维记录混在一起，读起来容易误判。值得让测试把日志
重定向到临时目录。

## 15. 2026-10-12：把"回滚之后"那一段接上，并顺手纠了一个**点不到**的界面

### 15.1 起因：缺口二不是代码缺口，是"路走不通"

14.3 记下的缺口二是：回滚把状态写成终态 `rolled_back`，而 `canary → approved_for_canary` 不是合法转移，
所以**回滚之后无法通过接口重新应用**；演练是用一次审计式人工修复绕过去的。交接文档给了两条诚实修法，
并指明第 ① 条（从同一聚类重新生成）**不需要动状态机**。本次就做 ①。

### 15.2 做法：不回滚状态机，产出**新**候选

`POST /code-candidates/{id}/regenerate`。旧行保持终态不动，新行从 `candidate_testing` 开始，重新走
沙箱 → 审核 → 批准 → 应用。守卫六条（状态、聚类状态、确认层级、堆放、观测归属、草案层级），
任一不满足即 409 且**一行都不写**；生成器的拒绝（超时/契约）也是 409 带原因，不留半条候选。

两个判断值得记：

* **"最新草案必须与确认层级一致"，不去找老的一致草案。** 第一版我写的是"newest-first 跳过不一致的"，
  听起来更宽容，实测被自己的用例抓住：重新诊断改了主意之后，它会**悄悄用一条老草案**接着生成——
  把"人已经改判"这件事藏起来了。改成只看最新草案、不一致就拒绝并说明原因。文档写"跳过不匹配"
  的时候我没意识到这正是"用老证据掩盖新证据"。
* **不放进 worker 轮里自动做。** 回滚是人的动作，"再试一次"也该是人的动作；`_eligible_patch_items`
  的注释本来就写着 regenerated patch 是"explicit administrator action, never a background retry"。

### 15.3 顺手纠的界面问题：应用栏放错了标签页（在 HEAD 上就错了）

给补丁详情加"回滚后重新生成"按钮时，我先把按钮加进了 `code-candidate-apply-bar`——然后发现**那个栏
自 HEAD 起就在「聚类」标签页里**（`git show HEAD:frontend/src/views/EvolutionCenterView.vue` 第 960 行，
在 clusters 分支、code-patches 分支之前），而它的两个按钮读的都是 `selectedCodePatch`。也就是说：
**五层门禁里"一键应用/一键回滚"在界面上从来点不到**（聚类页没有 selectedCodePatch ⇒ 两个按钮恒为 disabled），
补丁详情页里根本没有这个栏。后端接口与用例都是好的，坏的只是它挂在哪个面板。

本次把整栏移到补丁详情（审计列表与审核决策之间）。前端用例同时钉住：回滚态下应用按钮禁用、重新生成按钮可用；
点完重新生成之后，选中的新候选回到"不可重新生成"（状态已不是 `rolled_back`）。
**这一条是"看起来做完了、其实没人能用"的第五种形态**：端点有、用例有、页面里有按钮，但按钮在错的面板里。

和候选审计里留了行。

### 15.6 演练逼出来的两个状态表缺陷，当场修掉

演练不是只验证了功能，它把**状态表跟不上代码**这件事暴露了两面。两面都在这一步修了。

**一、`apply` 成功之后状态不动。** `#29` 确实跑进了工作树，但队列上仍是 `approved_for_canary`——
"已应用"只活在工作树与 `service-control.log` 里，而 `_clusters_with_open_candidates` 恰恰是按状态判断
"这个聚类还有没有未决"。回滚侧本来就有这一步（先写 `canary`，注释写着"让状态说的是事实"），
apply 侧没有。修法：apply 的前置检查与目标测试都过、补丁已在工作树里之后，把状态推进到 `canary`
（已在 `canary` 则幂等跳过，不重复写审计）。同时在 apply 的状态白名单里加入 `canary`，
让"已应用的补丁再点一次＝校验 + 重启"真的可用（界面上的提示语早就这么写了）。

**二、人手合进提交之后没有结案动作。** `#10` 的改动早在提交 `bcb645a` 里（在 HEAD 上
`git apply -R --check` 都失败），候选行却停在 `approved_for_canary` 两周，一直占着聚类 30 的准入名额。
系统无从知道人手合了什么，所以修法不是"自动检测"，而是**让管理员把这件事说出来并留痕**：
新审核动作 `close_out_merged` → 终态 `stable`（转移表加一条 `approved_for_canary → stable`）。
它**不轻信声明**：先按 `patch_state` 确认补丁在当前代码里、再按 `patch_is_committed`
确认那些路径相对 HEAD 干净（与回滚判定"改动来自提交"用的是同一个判据），任一不成立就 409 拒绝——
把"没上线"写成"已接受"是这条路径最危险的失败模式，所以它是 fail-closed 的。
备注里点名那次提交（调用方给不出就查 `git log -1 -- <paths>`），因为后来的人要能打开它核对。

**判据与验证**：后端新增 5 条用例（apply 推进状态、已 canary 幂等、结案落 `stable` 并释放聚类、
工作树未提交拒绝、改动不在代码里拒绝、未批准不允许结案）；全量 **2056 passed**（21 分 12 秒）；
前端加"已合入：结案"按钮（只在 `approved_for_canary`/`canary` 可用）+ 2 条用例，`vitest run` **215 passed**、
`vue-tsc -b` 通过、`npm run build` 已更新 `static/`。

**三、真机验证当场抓到的第三个洞（同一个动作）：`patch_is_committed` 分不清"干净"与"从未改动"。**
新代码上线后我拿 `#29` 做真机探针，本意是"改动还在工作树、应被拒绝"，结果**返回 200 结案成功**——
我先以为守卫漏了，核对后发现**服务是对的、我的预期是错的**：`#29` 的内容确实已经随提交 `d6fa7ad` 落地
（那正是我四个提交里的第四个），所以结案为 `stable` 是正确的。但这次误判暴露了一个**真实**的风险：
`patch_is_committed` 只查"这些路径相对 HEAD 干净"，而**一个从来没被改过的文件同样干净**——
拿一个假 diff 指向 `rag/reranker.py`，它也返回 true。若只看这一条，"根本没上线"可以被写成"已接受"。
修法：结案路径再加一道**内容核对**（`_added_lines_present_in_tree`）——把 diff 的新增内容行逐行到
工作树文件里找，注释行与空行有意排除（它们不能证明任何事）；只加注释的 diff 直接判"无法证明"。
`patch_is_committed` 的 docstring 也补了"它不能告诉你什么"，把这条边界写在调用点前面。
新增 2 条用例（真实现的正反两面 + 路径干净但内容不在），后端共 **2058 passed**。

**四、加了守卫之后再探一次，结果比"拒绝"更有价值：两条陈旧行都是真的。**
守卫上线后重启服务，我拿 `#20`（聚类 3 的 reranking 补丁，status `approved_for_canary`）再探——
本意是"这次该被第一道判据拒掉"，结果**又返回 200**。核对 `git log`：`#20` 的改动早在提交
`6dccf59`（"the reranker fallbacks stop truncating the recalled set"）里，`rag/reranker.py` 工作树与
HEAD 完全一致、`git show HEAD:rag/reranker.py` 里就有那行
`raise RuntimeError("Reranker returned no usable results")`。也就是说 **`#20` 与 `#29` 是同一种陈旧行**：
改动早已落地、候选行却停在 `approved_for_canary` —— 新动作一次抓出两条，两条的结案都是正确的。

代价是审计备注：两次我都把 `note` 写成 `probe`，而动作实际上是**如实结案**。审计行已落库、表带
CHECK 约束（动作枚举不可扩），所以这条措辞上的不精确只能在文档里更正 —— **这里如实记下**：
`#20`、`#29` 两条 `accept` 行的 `probe` 指的是"探针时随手填的备注"，不是"这次结案是假的"。
教训很小但很实用：**探针也要把备注写对**，因为探针留下的痕迹和真实操作留下的痕迹长得一模一样。

**这一条的教训**：真机验证的价值不在于"确认我以为的"，而在于**逼出我把预期写错的地方**。
上一个会话的 14.3、这次的 15.6，两次都是"接口行为与我的预期不一致"，两次都不是接口错。

**本轮结束时的队列**：`#20`、`#29` 为 `stable`；`#10` 为 `rejected`；`#26`、`#27` 为 `rolled_back`。
聚类 3 与 30 **都已无未决补丁**（这是结案的副产品：两条陈旧行不再占准入名额），
两个聚类随时可以重新生成候选 —— 这正是"修法 ① 的路没有被陈旧行堵死"的实证。

## 16. 2026-10-12（续）：层 2 的宿主对照第一次回流到门禁轨迹

**问题不是"缺功能"，是"东西有了、没人接上"——同一个形状这一轮第三次出现。**
`scripts/measure_patch_regression_ab.py` 跑完对照后只写 `artifacts/regression-ab-candidate-<id>.json`：
脚本里既没有 `CandidateStore`，也没有任何门禁写入。后果是三重的：

1. 五层门禁的**层 2「基准」从来没有真实的生产者**：沙箱按设计量不了回归（无凭据、fixture 描述的是
   另一份代码），而真正量了回归的那个脚本不回流 —— 于是"层 2 有结论"从不曾出现在候选自己的轨迹里；
2. #26/#27 的"两轮宿主对照"是**人在系统外读那个 JSON** 做的判断（这一轮的演练里我自己也是这么做的）；
3. 审查台因此对宿主对照**一无所知**：它渲染的是 `gate_log` 里的 `sandbox` 条目，而宿主那两次对照
   一行都没进去。

**修法：给"测量"一个不假装"决策"的写入口。** `CandidateStore.record_gate_entry()` 只追加
`gate_log` + 审计，**不碰 status**。这一条是整个改动的关键判断：宿主 A/B 是**给管理员决策用的证据**，
把它写成一个状态转移会把两件事混在一起（而且会让"测量"偷偷拥有推进候选的权力）。

**它还能写什么、不能写什么**：能做结果的是 `passed / failed / inconclusive / blocked`，
**刻意不含 `accepted`** —— 那是层 1 生成时的产物边界结论，后来跑的任何测量都不能替生成门禁说"通过"。
判据落在 `GATE_EVIDENCE_RESULTS` 常量上并有用例钉住：**证据可以量出失败，不能伪造准入**。
不达阈值的对照记成 `failed` 而不是拒绝写入 —— 数字本身才是重点，由人来读，这条路径从不推进任何终态。

**呈现上刻意分开**：详情响应给 `sandbox_summary` 与 `host_ab_summary` 两份，各画各的对照表。
写这一块时踩到一个**自己埋的坑**：前端 `sandboxMetrics` 原本在**整条 `gate_log`** 里按"有 verdict"找
最近的条目，而两个生产者的 `metrics.verdict` 形状相同 —— 宿主条目一进来就会被当成沙箱的结论画出来。
修法是只读 `sandbox_summary`，并加用例把"沙箱没有可比对照时不得被宿主数字冒名顶替"钉住。

**数字**：新增 5 条后端用例（store：追加证据不动状态、拒绝未知结果与层 1 的 `accepted`、未知候选；
sandbox：回流的 result/metrics/不动状态、没有可比对照时的措辞；api：两份摘要互不混入、没有对照时
显式 `inconclusive`）+ 1 条前端用例，全量后端 **2065 passed**、前端 216 passed。
**真机验证**：对已结案的 `#29` 跑了一次真实宿主 A/B（20 用例、每侧 2 次，10.6 分钟）——
输出里 `recorded_gate: "host_ab"`，接口详情里 `sandbox_summary` 1 条 / `host_ab_summary` 1 条，
轨迹变成 `scope → sandbox → review → review → host_ab`，而候选状态**仍是 `stable`**（测量不动状态）。
顺带得到一条真实数字：Jev 侧 route 1.0 → 1.0（Δ0.0pp）、Top-5 1.0 → 1.0（Δ0.0pp）、失败调用 0 → 0，
legacy 侧 Δ+2.5pp ⇒ `passed`。

## 17. 2026-10-12（续）：把"测试写进运维日志"这件小事收掉

**现象**（14.4 记过、坑清单里也记过）：跑一次全量套件，`artifacts/service-control.log` 里会多出
几行 `candidate 1: …`、`candidate 1 applied by admin` —— 接口用例走的是**真实的 apply/rollback
端点**，于是它们和真实运维记录写进同一个文件、长得一模一样。这一轮的演练里我读那个文件时确实被
干扰过：看到 `candidate 1 rolled back by admin (restart=True)` 愣了几秒才想起那是套件写的。

**修法：给日志目的地一个决定点，而不是让每个调用点自己拼路径。**
`service_control.service_log_path(repo_root)` 是唯一的决定点（默认 `<repo>/artifacts/service-control.log`，
可用 `RAG_EVOLUTION_SERVICE_LOG_DIR` 改道），API 的四处与 `spawn_restart_helper` 都从它取；
`tests/conftest.py` 加一条 autouse 夹具把它指到临时目录 —— 覆盖到每个写者：端点、
`spawn_restart_helper`、以及它交给分离助手的那个 `log` 字段。

**验证方式是"字节不变"**，因为它就是这个问题的判据：跑之前与跑之后对
`artifacts/service-control.log` 取 SHA256，跑完 `tests/test_code_candidate_api.py`、
`test_candidate_api.py`、`test_regenerate.py`、`test_code_review_fixes.py`、`test_api.py`（75 passed）
之后哈希**一字未变** —— 修之前这些用例每跑一次都会往里加行。

**顺带记一条方法论**：这个问题挂了两个会话没人动，因为它**不影响任何测试结果**——它只污染人读的东西。
它的成本落在"读日志的人要多想几秒"上，而这恰恰是自动化测试量不出来的那类成本。

## 18. 2026-10-12（续）：扩评测集（含多轮）——第一次抓到"单轮看不见的失效形态"

**为什么必须先做这个**：交接文档把"评测分辨率"列为唯一的结构性前提。它是这么算的——20 例里
一例翻转 = 5pp，而 #26/#29 的宿主 A/B 两轮结论从 −2.5pp 翻到 0.0pp，那 2.5pp 就是 40 个样本里的
**一个**用例。也就是说这套基准**只能证明"没变差"，证明不了"变好"**，而且会把噪声读成回归。

**这一轮做到了哪一步（如实分界）**：

* **跑分器支持多轮了**：用例可带 `history`（按时间顺序、以助手结尾，加载时当场校验角色与非空）；
  多轮改写按**用例自己的历史长度**打开；每次调用一个**独立会话 id**，所以"历史"里不会混进上一次的
  答案（共用一个会话时，第 2 次调用读到的历史 = 历史 + 上次的问答，两次测的不是同一个东西）。
  单轮用例完全不碰这些开关，行为逐字节不变。
* **新的多轮用例集**：`benchmarks/jev_multi_turn_cases.json`，7 例，每例 2 轮历史，追问本身不含
  先行词（"那它呢""那一步呢"）。**它是我写的，不是采集来的**——这一点必须说清楚：它是"多轮失效形态"
  的探针，不是那 20 例那样带真实证据标签的基准；要变成可决策的判据，得由人补真实问法与期望来源。
* **单轮 20 例仍 PASS**（回归确认）：准备 P50 805.9ms（旧 7541.4ms，−89%）、改写率 0.000、
  路由 1.000、Top-5 1.000 ⇒ 我的改动没有动到既有基准。

**然后它立刻抓到了一条真实的失效形态。** 多轮 7 例首跑：

| 路径 | 准备 P50 | route 准确率 | 改写率 |
| --- | --- | --- | --- |
| old（legacy） | 8719.5ms | **1.000** | 1.000 |
| new（Jev） | 467.8ms | **0.143** | 0.143 |

7 例里只有 `mt-001` 路由正确（那一句自带"模型"这个领域词），其余 6 例 `0/2`、**一次改写都没有**、
耗时只有约 280ms。形状很清楚：**新路径在路由层判"需要澄清"就返回了，根本没走到改写**，而路由层
只看当前这一句、看不到前面几轮；旧路径无条件改写，于是把"那一步"补全之后照常走 RAG。

**这一条的意义不在分数，在它是怎么被发现的**：既有 20 例单轮全是自带疑问词的完整问题，所以这个
失效形态在它们眼里**根本不存在**——基准的分辨率不是"样本太少"这一个问题，还有"**形态太单一**"。
这就是"扩评测集是唯一结构性前提"的实证：不是多测几次，是换一种问法。

**修法方向（未做，属于路由/提示词层，需单独验证）**：在 `route == "clarification"` 且该会话**确有
历史**时，先用历史改写一次再重新路由（只在多轮生效）；接受判据是先跑单轮 20 例（必须仍 PASS）
再跑这一集（route 应回到 1.000）。**不打算做的一件事**：下调 `route >= 0.95` 的阈值让报告变绿。

## 19. 2026-10-12/13（续）：#15/#16 的验证器并不是"沙箱"，以及一个不可重复的判定

**先把术语纠正过来**：交接文档写的是"#15/#16 跑沙箱，让队列里最后两条变成可决策"。跑之前一查，
`#15`、`#16` 都是 **`jev_question_set`**（纯数据的候选，没有 diff）——`scripts/run_patch_sandbox.py`
第 82 行会直接 `SystemExit("candidate N has no stored diff")`，**代码沙箱对它们不适用**。
它们真正的层 2 验证器是 `scripts/benchmark_candidate_questions.py`：把**线上问题集**与**候选问题集**
各回放一遍同一份固定语料（`jev_retrieval_cases.json` 20 例 + 已确认的 `real-cases-v1.json`，
共 44 例），两侧都交给 `candidate_gates.evaluate_on_benchmark` 判，阈值与代码补丁**同一套**。
（这一条值得记：交接里"跑沙箱"这四个字把人引错了工具，`#15/#16` 在待验证里躺了很久，
可能就因为它看起来需要一件对它不适用的事。）

**跑出来的东西比"两条待验证结案"重要得多。**

`#15`（干跑一次，只测不写）：`failed: top-5 hit dropped 5.0pp`（回归 real-007、real-009）。
`#16`：第一次干跑 **`passed: route delta +0.0pp, top-5 delta +0.0pp`**。

看起来是"一坏一好"，于是写回。写回那一轮（`--apply`，同样 44 例）却把**两条都判 failed、
且都是 `top-5 hit dropped 10.0pp`、回归用例也完全相同（real-007、real-009）**。
同一个 `#16` 前后矛盾 ⇒ 不可能是候选变差，只能是判定本身不稳。于是同一候选复跑两次：

| #16 的同条件测量 | 判定 | 基线 | 候选 |
| --- | --- | --- | --- |
| 干跑（第 1 次） | **passed** | route 43/44，top-5 19/20 | route 43/44，top-5 19/20 |
| 写回轮（第 2 次） | failed −10.0pp | route 42/44，top-5 19/20 | route 42/44，top-5 17/20 |
| 复跑 1（第 3 次） | failed −15.0pp | route 42/44，top-5 19/20 | route 42/44，top-5 16/20 |
| 复跑 2（第 4 次） | failed，route −2.3pp | route 43/44，top-5 19/20 | route 42/44，top-5 19/20 |

四次、同一候选、同一份语料：**passed → −10.0pp → −15.0pp → route −2.3pp**，而且**基线自己每轮都在变**
（route 43 或 42、top-5 命中 19/20 但失败的是**不同的用例**）。所以问题不是"20 例太少"这一条，
也不是"阈值太紧"：**判定在这份语料上不可重复**，而门禁把单次运行当结论用。

**这与之前那条"宿主 A/B 两轮翻转"是同一个病，只是这次量到了四次。** 15.5/16 节里 #26/#29 的
宿主 A/B 也从 −2.5pp 翻到 0.0pp，当时的说法是"当前分辨率下既测不出回归也测不出改善"。
现在能说得更准确：**不确定性的主要来源不是样本量，是判定层（Jev 的预判/段落判断）本身的随机性**
——基线侧的 route 准确率在两次运行之间都会变 2.3pp。

**这次已经落地的后果（如实记）**：`--apply` 那一轮把 `#15`、`#16` 都写成了 `rejected`，两条
`benchmark/failed` 条目就是上面第 2 行那次测量。也就是说**两条候选是被一次不可重复的测量判死的**。
我没有去改写这两行的状态（那需要又一次人工修复，而且会掩盖问题）；正确的处置顺序是：
先让判定可重复（多次取中位数/多数票，或把"一次运行"明确标成 inconclusive），再决定这两条。
**这是留给人的决定**，写在交接文档的未决事项里。

**顺带确认的两件事**：
* `--apply` 的 `--limit 5` 只处理了 `#15`、`#16` 两条未决问题集候选（轨迹里今天只有这两条
  `benchmark` 条目），没有波及别的行；队列现在 `stable` 2、`rejected` 20、`rolled_back` 6，
  **无任何待验证/待审核候选**。
* `benchmarks/real-cases-v1.json` 有真实证据标签，所以这 44 例里有 20 例是**带来源标签**的
  （`top5_labeled: 20`）——Top-5 判据只在这 20 例上算，一次翻转就是 5pp，这正是 −5/−10/−15pp
  这些数字的粒度来源。

## 20. 2026-10-13（续）：修掉多轮路由回归，并把"不可重复的判定"改成多数票

**一、多轮路由回归：只在"它说要澄清、而这个会话确有历史"时补一次改写并重判。**
新增 `RAGPipeline._route_with_history_correction()`（第 18 节那条回归的修法）：

* 没判澄清（rag/structured/tool/legacy）⇒ 原样返回，**零额外调用**；
* 没有历史、或改写结果与原问法相同 ⇒ 原样返回澄清，**零额外调用**；
* 有历史且改写确实改变了问法 ⇒ 用补全后的问法**重判一次**，按新决策继续；
* 改写不可用（异常）⇒ 退回原决策（补全失败不该变成路由失败）。

额外代价只有一次预判，且只花在"本来要拒答"的追问上；`query_rewrite_history_turns=0`（默认）时
改写不带历史、结果与原文相同 ⇒ 行为与修法前**逐字节一致**（用例钉住：无历史时路由只调一次、
改写函数一次都没被调）。

**修后复跑（真实模型，7 例多轮）**：`route` 从 **0.143 → 1.000**，多轮档案 **PASS**；
单轮 20 例仍 **PASS**（P50 831.6ms vs 6482.4ms、route 1.000、Top-5 1.000）。
**代价如实记**：多轮准备 P50 从 467.8ms（修前"直接返回澄清"的**假快**）涨到 11010.3ms，old 侧同用例
8877.6ms —— 新路径在多轮上不再是"比旧路径快一个数量级"，而是**同量级但答得对**。

**验收档案 `--acceptance`（阈值一个字没动）**：多轮档案把 p50/p95/rewrite 三条降为 **advisory**
（仍逐条打印、仍可读，但不再能否决报告），`executed`/`route`/`top5` 仍是硬判据。理由不是放水：
在多轮用例上**两侧都会改写**（实测 old 1.000 / new 1.000），单轮那套 "−30%/−20%/−70%" 描述的比较
已经不存在，拿它当门禁会因为"做了这件该做的事"而 Failed。**这是"哪几条判据适用于这一批用例"，
不是"把阈值调松"**——两者必须分清楚，否则下一步就是真的放水。

**二、判定不可重复：多数票 + 不稳定即 inconclusive。**
第 19 节量到同一候选四次得到 `passed / −10.0pp / −15.0pp / route −2.3pp`。新增
`evaluate_repeatable_on_benchmark()`：跑 `repeats` 次（**必须奇数**，多数票需要有裁决者），

* 任何一次因自身原因 inconclusive（基线侧崩）⇒ 整体 inconclusive；
* 各次对 pass/fail **不一致** ⇒ 整体 `inconclusive=True`，判定文字写明
  "did not agree with itself"，并把逐次记录（每次的 passed/两个 delta/verdict）放进 `stats["repeats"]`；
* 一致 ⇒ 保留多数结论，并在 verdict 后附上 `[3 repeat(s): 3 passed, 0 failed]`；
* `repeats=1` **逐字节等于**原 `evaluate_on_benchmark`（既有调用方与用例不受影响）。

`run_benchmark_gate(repeats=...)` 把它接进写回路径：**不稳定的判定不再写终态**，候选留在
`candidate_testing` 等重试 —— 这正是 `record_inconclusive_gate` 早就支持的语义，此前只用于
"基线侧撞上基础设施故障"，现在也覆盖"测量自己不一致"。

**门槛也没动**：`ROUTE_DELTA_MAX_PP=0.0`、`TOP5_DELTA_MAX_PP=2.0` 仍有用例钉着。

**三、#15/#16 的处置**：保持第 19 节写下的 `rejected` 不动（那两条的复核属于人的决定），
但**它们的证据现在已知不可靠**，交接文档里已注明。

**四、把"多数票"接到写回路径上（默认值改动）。**
`scripts/benchmark_candidate_questions.py` 新增 `--repeats`：**`--apply` 默认 3 次**，
只读回放默认 1 次（原行为）；偶数次直接拒绝（多数票需要裁决者，平票在这条路径上必须是一种未决）。
代价线性增长并写在脚本 docstring 里（一轮是"每候选每次重复几分钟"）；用例钉住默认值、显式值与
偶数的拒绝。也就是说：**下一批候选不会再被单次运行判死**。

**五、想把 #15/#16 重新判定一次，却发现两条路都不通（如实记）。**

* **回退状态**：`rejected` 是终态，`advance_candidate` 直接
  `ValueError: invalid transition: rejected -> candidate_testing`。上一会话在 `rolled_back` 上
  绕过终态靠的是**手改数据库**（审计里写着"人工修复"），那是它自己都记为设计缺口的事，
  我不重复那个做法。
* **设计里正道是"从同一聚类重新生成"**（`/regenerate`）：聚类 3 仍是 `approved_for_candidate`
  （layer=reranking，116 条草案），但**堆放守卫**会拒绝——聚类 3 还有一条"未决"补丁行 **#20**，
  而它是 `stable`（改动早已随 `6dccf59` 落地）。**这与 #10 是同一类陈旧行**：已落地、却仍以
  "未决"身份占着准入名额。所以 #15/#16 的重新判定要排在"把 #20 结案"之后。

**六、这一轮抓到的东西里，只有一个是代码缺陷，其余都是"衡量方式"的问题。** 14.3 的终态缺口、
15.6 的两个状态表缺陷、第 19 节的不可重复判定、以及上面第 5 条——**同一个形状反复出现：
制品做出来了，但没有任何东西负责把它交给下一个环节**（结果写进 JSON 没人读、测量不回流、
状态不跟事实走、判定不可重复却当结论用）。这条模式本身值得带到下一轮。

## 21. 2026-10-13（接手进展）：结案状态与堆放守卫解耦、单候选多数票接入与回放成本上限

**一、解开 `stable` 与堆放守卫（`_OPEN_CANDIDATE_STATUSES`）的死锁：**
* **发现与定性**：#20 早已通过 `close_out_merged` 结案并标记为 `stable`。但此前 `_OPEN_CANDIDATE_STATUSES`
  把 `EvolutionStatus.STABLE.value` 错误算作“未决”，导致聚类 3 和 30 在补丁合入后依然被永久判定为
  “已有未决候选”，堆放守卫彻底堵死后续演化；
* **修法**：将 `STABLE` 从 `_OPEN_CANDIDATE_STATUSES` 移除。已结案合入的补丁属于终态，不再占用聚类名额；
  未决集合严格收敛到 `candidate_testing / awaiting_verification / approved_for_canary / canary`；
* **验证**：聚类 3 与 30 的 open patch clusters 从 `{3, 30}` 恢复为 `set()`；新增单元测试覆盖
  `test_stable_candidate_does_not_block_future_candidates_in_cluster` 与
  `test_regenerate_allows_when_other_candidate_is_stable`。

**二、单候选回放真正接入多数票判定（修复闲置参数与未闭环）：**
* **发现**：`scripts/benchmark_candidate_questions.py` 之前只在 `--apply` 批量写回路径调用了
  `evaluate_repeatable_on_benchmark`；在单候选回放 `_run_single` 中，命令行传入 `--repeats 3` 却被
  完全忽略，依然调用单次 `evaluate_on_benchmark`（又是典型的“制品做出来了但没交给下一环节”）；
* **修法**：`_run_single` 统一切换到 `evaluate_repeatable_on_benchmark`，透传 `repeats=args.repeats`，
  并在报告中记录真实 `repeats` 轮次。

**三、回放成本安全上限守卫（`--max-total-runs`）：**
* **动机**：`--limit N --repeats M` 的耗时与调用量呈乘积增长；无限制的批量回放易导致限流或卡顿；
* **修法**：新增 `--max-total-runs`（默认 25）和 `--force` 开关，默认 `--limit` 调优为 5（5 × 3 = 15 次回放）；
  超限时显式报错拦截，提示降低批次或显式传参；补充 3 组针对性参数单元测试。

**四、多轮路由历史修正全分支单元测试覆盖：**
* 针对 `_route_with_history_correction()` 补齐 5 种场景的分支测试（无历史、非澄清、改写不变、补全重判生效、重判依然澄清），全量测试基线升至 **2102 passed**（+6 条测试，0 失败）。

**五、#15/#16 多数票真实重测落地（44 例语料 × 3 轮独立回放）：**
* **动机**：此前会话因单次运行的不稳定性（曾单次量出 passed），怀疑 #15/#16 被误杀、将证据记为“不可靠”；
* **真机重测结果**：
  * **候选 #15**：`[3 repeat(s): 0 passed, 3 failed]`，3 轮全败（Run 1: route -4.5pp, top-5 -5.0pp; Run 2: route -2.3pp, top-5 -5.0pp; Run 3: top-5 -15.0pp），稳定回归 `real-007` 与 `real-009`；
  * **候选 #16**：`[3 repeat(s): 0 passed, 3 failed]`，3 轮全败（Run 1: top-5 -5.0pp; Run 2: top-5 -10.0pp; Run 3: top-5 -5.0pp），稳定回归 `real-009`；
* **科学结论**：此前的单次 passed 属于偶然噪声；在多数票自洽机制下，**两条候选均确凿存在显著 Top-5 召回回归，维持 `rejected` 终态完全公正**。无需人工干预状态机，疑点彻底澄清。

## 22. 工程实践清单（这套代码里反复出现的做法）

1. **先定判据，再动手**：每项改动都先写"达标线"（如"生成成功率 ≥80%"），并留下对照数字。
2. **测量先行，且防自欺**：固定样本、串行执行（并行跑两条 A/B 实测触发服务商限流，让一次基线侧 26 次调用失败）。
3. **门禁要有牙齿**：失败是拒绝而非修补；不可比时显式标注（"没有数字 ≠ 没有变差"）。
4. **一切可回滚**：补丁导出为自描述文件 + 反向命令；应用失败自动还原；沙箱在隔离 worktree 里跑，
   主树字节不变。
5. **诚实的负面记录**：撤回无效的口径（并把测量留在注释里）、记录"不达标"的基线与自己的方法学错误。
6. **测试防固化**：彩排暴露了"夹具按错误假设塞字段"的问题之后，改为**按真实形态**构造夹具。
7. **不猜接口**：每个新代码都先读真实签名/表结构/schema，再写。

## 23. 诚实边界（面试时也会被问到）

* **系统永不自动合入**是设计红线，不是没做完；
* 黄金回放 fixture 对"触及外部 seam 的补丁"**按设计不可用**（录制描述的是另一份代码），这类补丁只能
  在带凭据的宿主上做 A/B；
* 结构化 `edits` 的 12/12 来自**一个聚类的 6 个观测 × 2 次**，结论强但**不外推**到别的层；
* 上游供给（真实失败流量）决定这套回路的产出速度 —— 没有流量时它诚实地空转（`scanned=0`）。
