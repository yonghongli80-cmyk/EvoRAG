# 开发日志（RAGv3 自演化系统）

> 这份日志按「**问题 → 证据（测量）→ 决策 → 结果（数字）→ 反思**」记录开发过程。
> 所有数字都来自仓库里的实测脚本，可复现；失败与返工也如实记录 —— 那部分往往比顺利的部分更值得讲。

## 0. 这套系统是什么（30 秒版）

一个**辅助式自我演化**的知识库问答系统：线上失败被记成"观测"，同类失败聚成"聚类"，由模型给出根因诊断，
经**五层门禁**（作用域 → 基准 → 影子 → 灰度 → 回滚）后产出三类制品 —— 提示词/查询改写候选、
**代码补丁**候选、**知识缺口工单**。**系统永不自动合入**：每一次变更都由管理员点击，
每条补丁都能一条命令回滚。

技术栈：Python / FastAPI / SQLite / Qdrant / Vue 3 + TypeScript / pytest / vite / ruff，
以及"用 `difflib` 合成 diff""用 `ast` 建符号索引"这类确定性工具的深度使用。

## 1. 2026-10-09：先让诊断可信，再谈自动化

**问题**：诊断（哪个环节坏了）是整条链的输入。此前靠启发式，中文诊断在英文代码路径上命中率为 0，
排序退化成文件字母序。

**证据与决策**：
* 管理员标签从 4 条扩到 **7 条**（每条附全库探针证据）；其中一条是**负向标签**——"内容在、金额被脱敏 ⇒
  价格答不出来是**正确行为**"，并**刻意不写型号串**，否则确定性包含检查会把这条脱敏确认误推成"取用侧缺陷"。
* 新增 `diagnosis-v10` **无证据护栏**：没有管理员标签却断言"库里没有"时，`root_cause` 必须写明"需管理员标签"
  （硬校验）——因为那个结论正是后续"知识缺口工单"的输入，不能让一次猜测变成一张工单。

**结果**：无标签 40 行开发集 **33/39 = 84.6%**，稳定行 35/39，契约违规 4/78（与旧版持平）；
此前 v8 的 31/39 **未复现** ⇒ 判定那次下降是噪声而非回归。

**反思**：一开始我把 v8 的下降当成回归；测量两次才敢说"是噪声"。**先定判据、再下结论**是这套系统能往前走的原因。

## 2. 2026-10-09：从"猜文件"到"点名文件"

**问题**：补丁生成器按"诊断措辞出现次数"排序文件。中文诊断贡献中文二字组，命中率为 0 ⇒ 退化为字母序；
证据边界的缺陷因此产出了三份改 `rag/agent.py` 的补丁。

**决策**：新增 `rag/evolution/symbols.py` —— 用 `ast` 建符号索引（143 文件 → 1696 符号，约 1.5 秒），
`_rrf_fuse` 直接解析为 `rag/retriever.py:230-266`；再用**靶心窗口**（目标行 ±120 行）代替"只给前 400 行"
——后者在目标位于第 745 行时什么也看不到。

**结果**（无模型调用的确定性验收）：无定位时首目标是"猜的" `rag/bm25_store.py`，有定位时是
**帧点名的 `rag/pipeline.py`**；窗口 `580–820` 覆盖第 745 行；中文诊断里的 `_finalize_rag_context`
与 `_rrf_fuse` 被解析为 `rag/pipeline.py` 与 `rag/retriever.py`。

## 3. 2026-10-09：彩排抓出"单元测试全绿但机制从不触发"

**问题**：worker 在生产里空转（`scanned=0`），"回路端到端可用"只有各部件用例，没有一条从观测走到制品的实证。

**做法**：在**数据库副本**上（SQLite backup API 取一致副本）注入三族失败并跑完整回路。

**结果与最关键的发现**：工单**一张都没产出** ✗。根因是**我自己的准入判据写错了**：它按聚类的
`root_cause_feature == "undetermined"` 判准入，而那是**聚类器**写的字段；"内容缺口"其实是**诊断草稿**的结论。
**我的单元测试之所以全绿，是因为夹具按我的错误假设塞了那个字段** —— 典型的"测试固化了错误假设"。
改为以最新草稿为准后重跑：**产出 4 张工单** + 3 份候选，三条不变量全部成立。

**反思**：端到端彩排的价值不是"再跑一遍"，而是它能证伪**你以为**成立的假设。这是我最愿意讲的一段经历。

## 4. 2026-10-10：把补丁生成成功率从 58% 提到 100%

**问题**：残余失败是"模型输出质量"，约每 4 次生成就有 1–3 次被边界拒绝。

**测量先行**：先建**测量台**（`scripts/measure_patch_generation.py`），复用 worker 同一套准入，
只读、不需要语料，输出成功率、失败类别、真实调用数（含重试）。
基线 **7/12 = 58.3%**（首试 41.7%）⇒ 距 80% 判据有差距，但**先有了可比基线**。

**基线顺带暴露一个自伤式缺陷**：5 个失败里有 2 个是 `timeout`，而生成器超时是**默认 90s、worker 从没传**
⇒ 等于**在截断一个慢但可能成功的调用**。修掉（默认 600s）后复测：不再有 timeout，但仍是 0/2 通过
⇒ 说明剩下的问题**不在超时**。

**关键判断**：两类上下文规模（400 行 / 1600 行）下，失败都以 `does_not_apply` / `corrupt_patch` /
"压根没给 diff"为主 ⇒ **上下文不是约束**；症结是**模型在手写 `@@ -a,b +c,d @@` 并核对行数算术**。

**决策**：加 `edits` 输出格式 —— 模型只给「路径 + 精确 `old_text` + `new_text`」，
**diff 由我们用 `difflib` 合成** ⇒ hunk 头与上下文**构造上自洽**，`corrupt_patch` 与 `does_not_apply`
在这条路径上不可能发生；边界一个字没改（路径白名单、黑名单、配额、`git apply --check` 照跑）
⇒ 是**双重保证**而不是放宽。

**结果**（严格同样本 6 对 × 2 次、串行）：`diff` **8/12 = 66.7%** vs `edits` **12/12 = 100%**（首试 100%、零重试），
单次耗时均值 110s → 59s。默认因此切到 `edits`，回退只需一个环境变量。

**反思**：我一开始做"加大上下文"的对照时**换了样本**（top-up 选了另一批），数字不可比 —— 这促成了
`--observation-ids`（固定样本）与帮助文本里那句"做 A/B 必须用它"。**测量本身也要防自欺。**

## 5. 2026-10-11：应用这一步的安全与"堆放治理"

**问题一（安全）**：批准之后的手工流程没有安全网 —— 没人检查补丁是否还能套用、改完还能不能导入、
服务起不来怎么办。

**决策**：`POST /code-candidates/{id}/apply`，三道前置检查（**能否应用** → **`import rag.api` 冒烟** →
**补丁自带的目标测试**），任一失败就**回滚并且不重启**；全过才写重启请求，由**分离式助手**执行：
等端口释放 → 拉起服务 → 轮询 `/health` → **起不来就回滚补丁再拉一次**（坏部署的结果是"旧代码在跑"，
而不是"什么都没在跑"）。应用前还会跑**全量套件** —— 因为补丁自带的 `test_paths` 是**模型自己挑的**，
拦不住"改坏别处"，那正是屎山的主要来源。

**问题二（用真实补丁暴露的两个 bug）**：
* 面板给出的应用命令带 `--3way`，而导出的补丁**没有 `index` 行** ⇒ 三路合并必然失败
  （`repository lacks the necessary blob`）—— 照抄就会踩 ✗；
* 同一份补丁"从文件能应用、从 stdin 失败"：`read_text` 把 CRLF 归一成 LF，而仓库文件仍是 CRLF ✗。
修法：命令与状态判断统一为**不带 `--3way`**，并且一律**写临时文件再 `git apply <file>`**（与运维命令同机制）。

**问题三（屎山风险，用户提出）**：查数据发现 **19 条代码补丁挤在 3 个文件**（`rag/reranker.py` 11 条、
`rag/agent.py` 7 条），其中 **5 条是同一个"同义对齐"想法的不同写法** ✗。根因是准入**按观测**去重，
而某个聚类有 **112 个成员** ⇒ 理论上一口气能产出 112 条。

**决策**：加**聚类级未决闸**（一个聚类只要还有一条未决候选，就不再为它的任何成员生成），
并且**轮内也挡**（轮初快照挡不住同一轮里的其他成员 —— 这一点是我写测试时才发现的，我的第一版修复有这个洞）。

**结果**：worker 套件 67 passed；两个聚类各得一条、再跑一轮零新增；驳回只释放**聚类级**闸，
不会让**同一个观测**自动重试（那条规则是有意为之）。

## 6. 2026-10-11（续）：把"手动重启"变成"一键重启"，并补上第三道闸

**问题一**：批准之后的手工流程没有安全网（补丁是否还能套用、改完还能不能导入、服务起不来怎么办）。
**决策**：`POST /code-candidates/{id}/apply` —— 三道前置检查（能否应用 → `import rag.api` 冒烟 →
补丁自带的目标测试）+ **应用前跑全量套件**（补丁自带的 `test_paths` 是**模型自己挑的**，拦不住"改坏别处"），
任一失败就**回滚且不重启**；全过才由**分离式助手**执行重启：停掉当前服务 → 拉起 → 轮询 `/health` →
**起不来就回滚补丁再拉一次**（坏部署的结果是"旧代码在跑"，而不是"什么都没在跑"）。

**问题二（我自己的 bug，被"手工做一次"抓出来）**：助手**从不停止当前服务** ✗ —— 它只等端口释放，
而按钮流程里没人释放端口 ⇒ 60 秒后它只会记一句"端口一直没释放"就退出 ✗✗，也就是**这个功能本来就是
不完整的**。是我**按你说的手动重启了一次**才发现的 ✓。修法：接口把自己的 pid 交给助手，助手先等几秒
（让 HTTP 响应先回到浏览器）再终止它，并在回滚路径里先结束**自己刚拉起的那个进程**（否则端口被它占着）。
另外补了一条用例：**助手源码是字符串，语法错只会在运行时炸 ⇒ 显式编译一次**。

**问题三（用户提出的"会不会变屎山"）**：查数据 —— **19 条代码补丁挤在 3 个文件**，
`rag/reranker.py` 11 条，其中 **5 条是同一个"同义对齐"想法的不同写法** ✗。
根因是准入**按观测**去重，而某个聚类有 **112 个成员** ⇒ 理论上一口气能产 112 条。
**决策**：① **聚类级未决闸**（一个聚类还有未决候选就不再生成，**轮内也挡** —— 这一点是我写测试时才发现
我第一版修复有这个洞）；② **应用前全量测试**；③ **近重复提示**（用 `ast` 符号索引把改动落到**具体函数**上，
键形如 `rag/reranker.py:Reranker.rerank`，两个以上同键就提示"这是同一条改动的变体，建议只留一条"）。
三道都是**提示/门禁**，从不自动改动代码 ✓。

**结果**：后端 **2015 passed** ✓、前端 **211 passed**（32 文件）+ 类型检查 + 构建 ✓；
「应用并重启」端点实测已在线（无令牌返回 401 = 路由存在 ✓）。

**另一份输入的核验**：另一 agent 提交了一份系统审计与升级路线图（`docs/rag-system-audit-and-upgrade-roadmap.md`）。
我逐条对照自己的测量：**多数与我的实测一致**（真实供给为 0、单文件补丁上限、20 例基准分辨率不足、
本地库锁瓶颈）。其中一条 P0 我**验证为真**并采纳：**用户点踩/投诉没有进进化池** ——
`POST /feedback` 只写 users 库的 `add_feedback`，**完全不碰进化队列** ✗。而点踩是**带人工标注**的最高信号失败源，
正是"供给为 0"最该修的地方。列为下一项。

## 7. 2026-10-11（再续）：把用户点踩接进回路（外部审计的 P0，我核验后采纳）

**来源**：另一 agent 提交的系统审计把"用户负向反馈未进进化池"列为 P0。**我去核验**了它 ——
`POST /feedback` 的实现只调用 `user_db.add_feedback(...)` 写用户库，**完全不碰进化队列** ⇒ **属实** ✓。

**为什么这条最值得先修**：整套回路的瓶颈是"真实失败供给为 0"（worker 诚实地空转 `scanned=0`），
而**点踩是带人工标注的最高信号失败源** —— 用户已经替你说了"这个回答不对"，还知道是哪一条消息。
修它同时解决**供给**与**标签**两件事。

**设计（每条都有理由）**：
* 走与 pipeline **同一个** `FailureRecorder`（非阻塞入队）⇒ 存储、跳过规则、阻断语义与线上一致，
  不另造旁路；
* `route="feedback"`：这是**用户报告**的失败，不是路由判定出来的 ⇒ 来源如实区分，聚类也能把
  "用户不满意"与"检索没召回"分开看；
* **只存结构化信号**（该消息的可答性/置信度/kb/有无留言），**留言文字绝不入库** ⇒ 那是用户内容，
  落在红线之外；
* 同一条消息**重复点踩不重复入库**（同一失败记两次是噪声，不是信号）；
* 整段 try/except ⇒ **记录失败绝不影响反馈本身**（用户点了踩就该成功返回）。

**结果**：3 条用例（点踩→观测且不含留言文字、空问题跳过、记录器抛错时反馈仍成功）✓。

**反思**：这一条不是我"想出来"的，而是**别人的审计 + 我去核验**得来的。两份输入的价值不同：
自己的测量能证伪自己的假设，外部审计能指出你根本没看的地方 —— 前提是**逐条核验**，
而不是照单全收，也不是不予理会（同一份审计里我采纳了这条，也明确不采纳多模态与服务型数据库那两条，
理由都写在给用户的回复里）。

## 8. 2026-10-11（三续）：端到端验收、同一失败模式的第二次，以及两条审计条目的核验

### 8.1 端到端验收（真登录 → 真提问 → 真点踩 → 真观测）

在**运行中的服务**上：登录 → 建会话 → 提问（一个语料里确实没有的问题）→ 系统诚实回答"资料不足" →
对该条回答**点踩** → 查询进化库：

```
obs#160 route=feedback 可答性=insufficient_evidence feedback=negative_with_comment kb=unknown
```

✓ 点踩落成观测、带结构化证据、**不含留言文字**（红线 ✓）。观测总数 158 → 160。

### 8.2 同一个失败模式的**第二次**：单测绿、接线没接

写完助手后我跑用例，**3 条全绿** —— 但线上点踩毫无效果。原因：我用 `replace` 插入处理器里的那**一行调用时没加断言**，
替换**静默失败**了 ⇒ 助手成了**死代码**，而用例**直接调用助手** ⇒ 当然全绿 ✓✗。

这与第 3 节（彩排抓出"单元测试固化了错误假设"）是**同一类失败**：**测了部件、没测接线**。
本次的修法：① 插入时**断言**替换真的发生 ✓；② 补一条**端点级**用例 —— 走 `POST /feedback`、断言观测助手**真的被调用**
（正向反馈则不调用）✓✓；③ 失败也要留痕：把观测记录失败写进 `artifacts/feedback-observation.log` ✓
（正是这份日志帮我在"静默失败"里定位到 `user_id` 漏传那一步 ✓）。

顺带修的两个小问题：漏传 `user_id`（`TypeError` 被 except 吞掉 ⇒ 观测根本不落库 ✓）；
`ExecutionTrace.decision_metadata` 有**键白名单**，我在元数据里放的溯源键被静默丢弃 ⇒ **去重形同虚设**，
已把 `feedback_message_id` 加入白名单 ✓。

还有一条**操作教训**：我的手工重启是 racy 的 —— `kill → 等 4 秒 → start`，若端口未释放则 `start.py` **拒绝启动**，
而**旧进程继续服务** ⇒ 健康检查通过、请求却打到旧代码上（实测：13:38:08 的点踩打到旧进程，13:38:29 新进程才起来）。
正确的判定是**比较进程启动时间与源文件修改时间** ✓（正是我写的重启助手做的事：等端口真正释放 ✓，
粗糙的是我手工那几步）。**这条也说明"手工流程不可靠"，正是做一键重启的理由。**

### 8.4 「看起来对了、其实什么都没做」的三种形态（同一功能里连着踩了三次）

点踩这条功能，我连着遇到**三种不同的静默失效**。它们的共同点是：**单测全绿、接口照常 200、日志干净**，
而实际上什么都没发生。值得单独记下来，因为这类 bug 比崩溃难查得多：

| # | 形态 | 为什么看不见 | 怎么暴露的 |
| --- | --- | --- | --- |
| 1 | **接线漏了**：处理器里那一行调用没插进去（`replace` 静默 no-op），助手成了死代码 | 用例**直接调用助手** ⇒ 全绿；接口返回 200 与以前一模一样 | **在运行中的服务上真的点一次踩**，再查库 |
| 2 | **参数漏传**：`get_message_reliability(message_id)` 少一个 `user_id` ⇒ `TypeError` | 被宽泛的 `except` 吞掉（当时的日志只在服务进程里、而服务是分离启动的 ⇒ 看不到） | 在进程内**逐步复现**那条路径，让真实异常打出来；并补上可查的失败日志 |
| 3 | **键名读错**：去重读 `decision_metadata`，而存储返回的是 `details_decision_metadata` ⇒ 永远 None | 去重"看起来"在跑，只是从不命中 | 打印**真实行**的键名，用真实键名补一条行为用例 |

**教训（写给未来的自己）**：
1. **部件测试不等于接线测试**：对"必须发生"的调用，要有一条**走端点**的断言（本次补了两条）；
2. **宽泛的 `except` 必须有可查的留痕**，否则它会把"功能没生效"变成"什么都没发生"；
3. **凡是读存储的代码，键名要按真实行的键名写**，并用真实形态的夹具钉住（真实键名、真实前缀）；
4. **最后一步永远是"在真实环境里跑一遍并核对数据"** —— 本次三处都是这样才暴露的。

**顺带**：这次也确认了"手工重启不可靠"（racy：旧进程还在服务时，健康检查会骗过你），
而**判断标准是"进程启动时间是否晚于源文件修改时间"** —— 这条已用于验证服务是否真的带上了修复。

### 8.3 两条审计条目的核验

| 条目 | 结论 | 证据 |
| --- | --- | --- |
| 多轮对话上下文改写缺失 | **属实** | `rewrite_query(question: str) -> str` **只吃当轮问题**，拿不到会话历史 ⇒ "它呢？/那这个多少钱？"这类指代会被**无上下文改写** |
| 文档切块结构损坏（表格/行截断） | **未能证实（我先写成了"属实"，那是我错了）** | 详见下面的"三次坏指标" —— 我用三个**不成立**的代理指标得出过结论，每一个都被后续测量推翻 |

#### 关于切块：我连错三次，最后**撤回结论**

审计说"表格与行被截断"。我先给了"属实"的结论，随后自己把它推翻了三次：

| 我的假设 | 怎么被推翻的 |
| --- | --- |
| "行比块还长，所以被迫切进行里" | 量出来：该库 820 行，长度中位数 **60**、90 分位 **75**、**最大 348** ⇒ 没有一行超过 `chunk_size=500` |
| "通用切块器的 `chunk_overlap=80` 泄漏出半行" | 在**真实源文档**上做修复前/后对照：**首行落在行中 = 0 / 0** ⇒ 空操作；而库里 104 块**全部来自 5 个 `.xlsx`**，且**没有 `chunk_kind` 元数据** ⇒ 它们根本不是表格切块器产的，长度画像 472/500 指向通用切块器 |
| "首行以数字/制表符开头 = 半行碎片" | 文本化的表格里，一块**合法地从表格中间某一行开始**时，首格是数字完全正常 ⇒ 这个指标把"从某行开始"误判成"从行中间开始" |
| "列数不一致 = 行被切开" | 按单文档看：`camera-battery-charger.xlsx` 是 11 列(56%) 与 **13 列(107 行)** ⇒ **13 > 11 不可能是切开**（切开只会更少）⇒ 那些 sheet 里本来就有多张形状不同的表 |

**结论：这条我无法复现，因此撤回"属实"的结论。** 我确实留下了一个**有测试的防御性改动**
（把块首对齐到行边界，防止将来把 overlap 调大后真的吐半行 —— 在真实文档上实测**零行为变化**），
但它是**防御**，不是这个缺陷的修复。**能定论的下一次检查**是：用 `rag/spreadsheets/parser.py`
解析真实 `.xlsx`，逐行比对索引里的行是否等于**整行** —— 那才是能分开"多张表"与"被切开的行"的证据。

两条都动了**线上路径**（查询改写、切块），属于人工改动或由回路提案的层级 —— 已把证据记在此处，
列为下一步的候选工作，而不是顺手改掉。

## 9. 工程实践清单（这套代码里反复出现的做法）

1. **先定判据，再动手**：每项改动都先写"达标线"（如"生成成功率 ≥80%"），并留下对照数字。
2. **测量先行，且防自欺**：固定样本、串行执行（并行跑两条 A/B 实测触发服务商限流，让一次基线侧 26 次调用失败）。
3. **门禁要有牙齿**：失败是拒绝而非修补；不可比时显式标注（"没有数字 ≠ 没有变差"）。
4. **一切可回滚**：补丁导出为自描述文件 + 反向命令；应用失败自动还原；沙箱在隔离 worktree 里跑，
   主树字节不变。
5. **诚实的负面记录**：撤回无效的口径（并把测量留在注释里）、记录"不达标"的基线与自己的方法学错误。
6. **测试防固化**：彩排暴露了"夹具按错误假设塞字段"的问题之后，改为**按真实形态**构造夹具。
7. **不猜接口**：每个新代码都先读真实签名/表结构/schema，再写。

## 10. 诚实边界（面试时也会被问到）

* **系统永不自动合入**是设计红线，不是没做完；
* 黄金回放 fixture 对"触及外部 seam 的补丁"**按设计不可用**（录制描述的是另一份代码），这类补丁只能
  在带凭据的宿主上做 A/B；
* 结构化 `edits` 的 12/12 来自**一个聚类的 6 个观测 × 2 次**，结论强但**不外推**到别的层；
* 上游供给（真实失败流量）决定这套回路的产出速度 —— 没有流量时它诚实地空转（`scanned=0`）。
